Android アプリは Kotlin + Jetpack Compose のネイティブパッケージで、ローカルのデータ層に Room/SQLite を使う。**多利用者のサーバークライアントではなく、単一利用者のアプリケーションパッケージである。** DDL の解釈・Stage 1.5 の展開・Score の補修・SVG の描画・履歴メタデータ・キャンバス比の値・render hash の意味論については、**サーバー／Web が開発の master であり続ける**。Android 固有の UI 判断は、**明示的なモバイル相当か、文書化された省略**であるときにだけ許される。

Android のローカル LLM 対応は LiteRT-LM を使い、標準のローカルモデルを Gemma 4 E2B、より高品質な選択肢を Gemma 4 E4B とする。モデルのライセンス同意・ダウンロード状態・再ダウンロード・チェックサム検証・モデルファイルのパスは Room に保存する。**LiteRT-LM の GPU バックエンドが必須で、CPU フォールバックは Android の挙動に含まれない。**

Android はモデル選択を、指示文生成・Stage 1・Stage 2 に共通の描画モデル 1 つへ単純化する。ただし設定・JSON 表示・書き出した JSON・履歴レコード・描画メタデータでは、サーバー互換の `stage1_model` と `stage2_model` のフィールドを保つ。モデル設定ページは、サービスの追加・サービス名とベース URL の編集・API キーの追加と削除・プロバイダのモデル一覧の取得・公開モデルの選択のための、プロバイダのパネルを出す。**接続の種別はサービスを作るときに決まり、既存のサービスパネルからは編集しない。** 取得した候補モデルは、描画モデルの選択に出る公開モデルとは別に保存する。

Android の描画ビューはモバイル固有の操作を提供する — ピンチによるズーム、パン、履歴移動のための左右のスワイプ、ダブルタップのプレゼンテーションモード。プレゼンテーションモードは他の UI を隠し、画像を中央へ置き、縦持ちの端末では横長のキャンバスを回転させ、描画された画像の背景から周囲の背景を選ぶ。**白背景の画像には暗いアプリ背景を、黒背景の画像には明るい背景を使う。**

Android の履歴ビューは、**意図してサーバー／Web の UI と異なる。** 3 列のサムネイルグリッドを使い、ゴミ箱・リスト表示・一括選択・ユーザー管理・DB 管理・プラグイン管理・サーバーログの操作を省く — Android パッケージが単一利用者でモバイル優先だからである。

Android の SVG／PNG 書き出しはサーバー／Web の `CanvasPanel` の意図に従う。SVG の書き出しは display・editable・compatibility のプロファイルを持つメニューである。PNG の書き出しは Room の `export_templates` に支えられたメニューで、y 軸の既定は `1080px`・`2160px`・`4320px`。**Android はブラウザのダウンロードではなくプラットフォームの共有シートを開く。**

Android の描画メタデータは `render_canvas_aspect_id` と `render_canvas_aspect_ratio` を含む。いずれもサーバー／Web のシステムプラグインから移植した同じキャンバス比の定義から導く。Android のヘッドレス描画・比較の道具立ては Compose の UI 無しで走れ、サーバー CLI の `--input-mode ddl` の流れと合わせて、DDL から描画・Score から描画の対応を比べるのに使う。

**Android の版数は Web の Build 番号から独立している。** `android/VERSION` が Android の `versionName` の元、`android/BUILD_NUMBER` が `versionCode` の元である。v1.48 の世代では、Android の値は `1.48.0-android.1` と `148001` から始まる。Android の設定メニューは、版名・版コード・ビルド種別・アプリケーション id・元となる仕様の世代・render engine の版数を含む版の詳細を出す。

履歴レコードはサーバー側の `render_hash` を持つ。新しいレコードは描画メタデータの節が定める `rh2:<sha256>` のエディション ID の意味論を使う — **保存された Score と明示の描画条件であって、SVG のテキストではない。** 従来の 64 文字のハッシュは表示互換のまま残る。履歴 API・paint／compose の応答・JSON タブ・保存済み作品の JSON は、`render_hash` と、人が参照するための 4 文字の大文字 `render_hash_short` の両方を出す。履歴マネージャはサムネイルの配置を変えずに短いハッシュを見せ、押すと完全なハッシュを複写する。ステータスバーもスター操作の隣に現在の描画の短いハッシュを見せ、押すと完全なハッシュを複写する。Web UI が履歴 API を通じて描画を保存したあと、実行中の結果のハッシュを DB の履歴レコードのハッシュへ置き換える — **描画直後に見える値と、あとで同じ作品を履歴から選んだときに見える値が一致するようにするためである。** CLI はハッシュの後方一致を解決でき、曖昧な短い一致は拒否し、ベンチマーク講評のために選んだ履歴項目や範囲を書き出せる。

履歴マネージャは現在のビューポートの 80% で開き、左右に 10% の余白を残す。サムネイルカードは、小さなスター／ハッシュ／操作の行の上に記述のプレビューを見せる。記述のプレビューは `#12` のような先頭の数字マーカーを省き、小さなサムネイルの操作はライトとダークの両方で見えるコントラストを保つ。履歴マネージャのページングは重なった取得を追跡するので、最後の要求が終わった時点で読み込み表示が消える。サムネイルのページングはダイアログのサムネイル領域を実測し、**サムネイルのスクロールバーが出ずに収まる数だけ**を動的に使う。サムネイルのスター操作はカードの選択から切り離してあり、ページの大きさは実測したカードの高さを使って、ダイアログ下部の余りを減らす。サムネイルの操作行はスターを左下に置き、ハッシュのラベルを `#` 無しで見せ、ハッシュのボタンの字面を削除操作と揃える。スター付きのサムネイルはダークモードでも明示のハイライト状態を保つ。**履歴マネージャのサムネイルはホバーで拡大プレビューを開かない** — グリッドと選択の操作を安定させるためである。履歴マネージャのヘッダは 2 行へ圧縮し、1 行目に題／表示／件数／ページャ、2 行目に選択／絞り込み／検索を置く。実測したカードの寸法からサムネイルのページの大きさを計算し直したときは、**先頭ページへ飛び戻らずに現在のページ番号を保つ。** 履歴マネージャの項目ごとの削除操作は、文字のラベルではなく小さなゴミ箱アイコンのボタンを使う。

JSON タブ・paint の応答・履歴レコード・保存済み作品の JSON は、サーバーが実際に使った `stage1_model` / `stage2_model` を含む。**現在の色管理は意図して sRGB に限る。** JSON タブ・paint／compose の応答・履歴レコード・保存済み作品の JSON は `render_color_profile: { id: "srgb", name: "sRGB IEC61966-2.1", standard: "IEC 61966-2-1:1999" }` を含む。Adobe RGB その他の広色域プロファイルは将来の拡張候補のままで、現行の renderer には実装していない。JSON タブは描画メタデータ（モデル・Build・色プロファイル・render engine・キャンバス比・色カタログのフィールド）を先に表示し、そのあとに `score` のペイロードを置く。履歴の項目を開き直したとき、JSON タブはその履歴レコードに保存された `stage1_model` と `stage2_model` を表示する。

paint・compose・履歴レコード・JSON タブ・保存済み作品の JSON は render engine のメタデータも含む。`render_engine_id` は JSON Score を演奏した描画中核を、`render_engine_version` はそのエンジンの契約の版数を指す。**これらは正規の `render_hash` のペイロードに含める** — 入力の Score が似ていても、異なるエンジンで描かれた 2 つの作品が追跡できるようにするためである。

設定ダイアログは管理者専用のモデル設定タブを持つ。既定の Stage 1 / Stage 2 のプロバイダとモデル、およびプロバイダごとのベース URL と API キーの設定を、サーバーのアプリ設定へ保存する。対応する接続先は OpenAI API Platform・Claude API・Gemini API・NVIDIA NIM・Ollama の OpenAI 互換 API・Ollama Cloud である。管理者はモデル設定タブから接続サービスを追加・削除できる。追加したサービスはサービス ID・表示名・接続種別（`openai_compatible`・`anthropic`・`gemini`）・ベース URL・任意の初期 API キーを持つ。サービス追加ダイアログは「追加」を押した時点で新しいサービスをサーバーへ保存するので、**サービスパネルにパネル全体の保存ボタンを重ねて置かない。** モデル一覧は、サービスを作るときに手で打つのではなく、あとから各サービスのモデル一覧取得の操作を通じて取る。

**サービス ID は、DB の接続設定・Stage 1 / Stage 2 のプロバイダ参照・API のプロバイダ振り分け・重複防止に使う安定した内部キーなので、作成後は編集できない。** 利用者に見えるサービス名はあとから編集できる。

各サービスパネルは、サーバーを通じてモデル一覧を取得できる。サーバーは保存されたベース URL と API キーを使ってプロバイダ固有のモデル API を呼び、返ってきたモデル一覧をそのサービス定義へ保存し直す — **生の API キーをブラウザへ送ることなく行う。** 取得の成功・失敗の文言は、公開モデル選択ダイアログの下部に出る。

**生の API キーはサーバー側にだけ置く。** UI が `GET /api/settings/models` を使うのは、キーが設定済みかどうかを知るためだけである。生のキーがブラウザへ返ることは決してない。キーが設定済みのとき、入力欄は「保存済みのキーを保つ」と表示して読み取り専用になる。未設定のサービスへ新しいキーを入れると、そのサービスの操作がキーの保存へ変わる。`PUT /api/settings/models` はプロバイダのキーの保持・置換・消去を区別する。プロバイダの API キーは暗号化した `enc:v1:` の形で DB に保存する。サーバーは `INKU_SECRET_KEY` が設定されていればそれを使い、無ければ `INKU_SECRET_KEY_FILE` か `~/.local/share/inku/secret.key` をローカルの鍵ファイルとして使う。既存の平文のキーは互換のため読めるままで、次の保存時に暗号化保存へ移す。モデル設定タブは、AI サービス接続の見出しの隣にこの規則を示す — **API キーは DB で暗号化され、二度と表示されず、環境変数で設定したキーは初期値として扱う。**

モデル参照は 3 段で解決し、**推測では決して解決しない**。①明示のプロバイダ接頭辞が勝つ（`openai:...`・`anthropic:...`・`gemini:...`・`nvidia:...`・`ollama:...`・`ollama-cloud:...`）②そうでなければ、設定済みのプロバイダのうち**ちょうど 1 つ**がそのモデル ID を並べているならそれを使う ③そうでなければ、その段に設定されたプロバイダを使う。プロバイダ ID はコロンを含めないので、**最初のコロンだけが分割点になりうる** — したがってモデル ID はコロンをいくつ持ってもよい（`qwen3.5:4b-q4_K_M`）。2 つのプロバイダが提供するモデル ID（`gpt-oss:20b` は Ollama と Ollama Cloud の両方が提供する）は、**意図して第 2 段では決めない。** 以前のフォールバック（スラッシュがあれば NVIDIA、`gemini-` の接頭辞、そして何でも受ける総取りのプロバイダ）は無くなった — どのカタログにも無い裸の文字列は、**モデルの提供をやめて久しいのに `/health` にだけ答えていたプロバイダへ黙って流れるのではなく**、その段のプロバイダへ行く。そのプロバイダ、Intel OVMS は 2026-07-30 に丸ごと撤退した。**撤退したプロバイダは、読み込み時に保存済み設定から落とされ、どこにも提示されず、接続を受けるのではなく例外を上げる。** ただしそのモデル id は読めるままなので、そこで作られた作品はいまも名前を持つ。

画面上でモデルが名指しされるところ — 実行中の表示、作品の Stage 1 と Stage 2 の行、履歴の表、系譜ノードの詳細 — はすべて `<プロバイダ> / <モデル>` の形で名指しする。**モデル id だけではどこで走るかを語らず、`gpt-oss:20b` が 2 つのプロバイダから提供されている以上、一意ですらないからである。** 例外はモデル選択で、そのカードは既にプロバイダの見出しの下に並んでいる。

Web UI は `/api/paint`・`/api/interpret`・`/api/compose` へ送るモデル ID を、選ばれたプロバイダと選ばれたモデルを組み合わせて正規化する（例: `openai:gpt-5.2`）。保存されるユーザーごとのモデルの選択はプロバイダとモデルの対で、古い単一の修飾済み文字列も読み込み時には受け取って対へ分割する。デモの記述生成も、OpenAI API Platform・Claude API・Gemini API・NVIDIA NIM・Ollama・Ollama Cloud について同じプロバイダ解決の経路を使う。**Ollama Cloud は自身の並行上限を宣言しており、サーバーはそれを設定として出すのではなくプロバイダごとに強制する。**

LLM サーバーの接続設定は、管理者が管理する全体設定である。各利用者の Stage 1 / Stage 2 のプロバイダとモデルの選択は `user_accounts.model_settings` に別途保存し、モデル選択ダイアログから `/api/auth/me/settings` を通じて保存し、ログイン時に復元する。管理者はプロバイダごとに、どのモデルを利用者に見せるかを切り替えることもできる。公開モデルの選択は、モデル一覧の取得・検索・全選択・全解除も含む別のダイアログで扱う。**そのダイアログの中のチェックボックスの変更は手元の下書きであり、保存を押したときにだけサーバーへ送られる。** 取り消し、またはダイアログの外を押すと破棄される。主となる設定タブは、いま公開されているモデルの要約だけを見せる。`GET /api/models` はログイン中の利用者へ公開モデルだけを返し、モデル選択ダイアログはその絞り込まれたカタログを使う。

ステータスバーの PNG 書き出しテンプレートの既定は、y 軸の高さ `1080px`・`2160px`・`4320px` である。保存済みの古い既定 `1024px` と `2048px` は自動的に新しい既定へ置き換わるが、**利用者が手を入れたテンプレートは保たれる。** 日本語 UI ではこの寸法を `Y軸` / `Y軸の高さ` と表示する。

### v1.51（2026-07-02）

v1.51 は関係の仕組み（日本語では「あいだ」）を足し、揺らぎをミクロとマクロの両方のスケールへ割り当てる。JSON Score の命令は、renderer が解決する配置のための `at.region` と、直前の命令に対する観察可能な関係のための `relation`（`along`・`not_touching`・`cutting`・`between`）を持てるようになった。renderer の演奏は `render_seed` を記録するので、マクロな配置は演奏ごとに変わりつつ、seed を与えれば再現できる。

Stage 1.5 は固定の完成レシピから離れ、**構図族の選択と関係の付与**へ向け直した。妥当でない関係は補修せずに落とし、**coerce 層が関係を足すことは禁じる。**

詳細な実装の履歴は正本の日本語仕様に残る。

### v1.52（2026-07-04）

v1.52 は事後選択を、2 つの明示的な再生成の経路として実体化する。`render_seed` は LLM 呼び出し無しの「別の演奏」を支える。`composition_seed` は Stage 1.5 の選択 seed へ明示のカウンタを混ぜることで「別の構図」を支え、**同じ入力が同じ展開を生むという既定の規則は保つ。** vary の経路は構図族・焦点・技法の選択を変え、Stage 1 の解釈を意図的に変えることはしない。

v1.52 は**補修部品がシステムの指紋になることも禁じる。** CLI の多様性分析は、マーカーに基づく補修部品の件数と標本率を報告するようになった。coerce の補修部品は固定座標ではなく入力由来の配置と形の変化を使い、隣接する焦点の反応は孤立した視覚的な出来事のときにだけ発火する。

Build 442 の検証で `composition_seed` の経路が API・CLI・Web UI を通じて実装されていることを確認した。5 記述 × 5 vary の実行は 25/25 で成功しフォールバック無し、日英 30 標本の補修部品の測定で `adjacent_reaction` は 56/60 から 14/60 へ下がった。

**Build 442 はベンチマークの受入ゲートを満たさなかった。** `angular_pulse` は 14/60 のまま、`vanishing_trace` は 21/60 から 26/60 へ上がり、`visual_event` の平均は Build 441 の基準 93.0 から 77.8 へ落ちた。

### v1.70（2026-07-08）

v1.70 は美的選択の段階を実装する — **judge の指標を受入ゲートの外に置いたまま**、形・事後選択・比較を製品の中で見えるようにする。

- 言語と仕様の整合の見直しで、「ランダムに散らす」のような記述者に向けた語は妥当な入力のままであり、**無秩序なランダムさは内部の Score 表現としてのみ禁じられる**ことを明確にした。コアの色語彙は記述者に向けた 6 つの抽象色のままで、色カタログはサーバー所有の解決メタデータであって語彙の拡張ではない
- 記述面は、静かで妨げない長さのヒントだけを持つ — 日本語でおよそ 31 文字、英語でおよそ 12 語
- 歳時記の関係の項目は詩的な見出しを保ちつつ、例では到達可能な固定の「前の対象」の句を示す。Stage 1 は**明示的に書かれた要素間の関係だけ**を関係の句へ正規化する。川岸のような場所や情景の語における「沿って」は関係の述語ではない
- 事後選択が具体になった — 変化のグリッドは既定で 4 候補を生み、新しい解釈候補を任意で含め、複数選択を許し、選んだ作品を履歴へ保存できる。スター付きの履歴項目は、選んだ理由を説明する短い任意の注記を持てる
- 明示の解釈の変化は `interpretation_seed` を記録し、正規化 DDL の差分を表示する。**再現は、LLM の非決定的なテキスト出力の再生ではなく、保存された DDL / Score に錨を下ろす**
- 参照語彙プラグイン `Nature` が `Nature.wind`・`Nature.undulation`・`Nature.stillness` を決定的な Stage 1.5 のマクロとして足す。**明示の `Nature.` 名前空間が必須**で、素の自然言語の語ではプラグインは発火しない。実装は既存の DDL / Score の変化と arrangement だけを使うので、新しい primitive・Score のフィールド・coerce の規則は 1 つも足していない
- 歳時記は Nature プラグインの語を、別のプラグイン区分として控えめな独自の体裁で見せる
- 比較の領域は、前回と今回の描画を並べ、控えめな記述の差分と、2 つの Stage 1 モデルのための LLM Model Inspection ビューを見せる。**これは鑑賞の道具であって judge の面ではなく、judge 値を 1 つも表示しない**
- 主要な操作へ地域化されたツールチップを足した（4 候補のグリッド・解釈の変化・選択の保存・モデル比較・DDL の自動補修）。ツールチップの文言は主 UI の言語切替に従う
- 左の App rail はマウスのホバーで広がらなくなった。幅は左上の明示の開閉トグルが制御するので、**編集中も作業領域が安定したままでいられる**
