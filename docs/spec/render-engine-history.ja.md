# render engine の版史

**演奏（描画）の版だけを、新しい順に 1 版 1 節で並べた索引である。**
inku は同じ JSON Score から毎回わずかに違う絵を出す。**その「出し方」の版が render engine 版**で、
製品の版数（`v2.7.8` など）とは別に数える。**この文書はどの版で何が変わったかを引くための入口**であり、
詳細は各節が指す先にある。

**この文書が新設されるまで、1 つの版から 15 までを通して見られる場所はどこにも無かった。**
記録は 4 箇所に散っていた（2026-07-28 に本書へ集約した） — 英語 `SPEC.md` の散文（engine 5〜10）、日本語 `SPEC.ja.md` §15.9〜15.11（13〜15）、
`server/reference/README.md`（12 と 15）、そして CHANGELOG の版エントリ。

## 版を上げる条件

下の「版と同一性 ID」が定める。**2 つある。**

1. **同じ Score と同じ seed から出る演奏結果が変わったとき**
2. **演奏できる語彙が増えたとき**（描画が 1 バイトも変わらなくても上げる）

**改名では上げない。** 逆に、**上げたら参照コーパスを凍結する** — その版が動かしたケースの SVG だけを
`server/reference/render-engine-<版>/` に置き、manifest が全ケースの digest を持つ。

**DDL 変換層（`DDL_ENGINE_VERSION`）はもう一つの条件を持つ** — **`Instruction` のフィールド宣言順を
変えたとき**である。Stage 2 の tool schema は並び順ごと LLM へ渡り、**任意フィールドの充填率は宣言位置に
単調に従属する**（先頭 0% → 末尾 89%。実測は `SPEC.ja.md` §5.1）。**振る舞いを 1 行も変えていなくても
Score の分布が変わり、絵が変わる。** 並べ替えは「読みやすさの整理」に見えるので、**この条件だけは
凍結コーパスで捕まえられない** — コーパスは Score を固定して演奏を見る検査であり、
Score そのものの分布が動く変化は 1 件も動かさない。

**この条件が最初に適用されたのは `ddl_engine_version` 2 → 3（v2.9.5・2026-07-29）である** —
`Instruction.thinness` を 14 番目から末尾へ移し、搬送が 18% から 89% になった。
**焼いた `ddl-engine-3/` は 29 ケースが `ddl-engine-2/` とバイト一致で、`changed_from_previous` は空**。
**その空白が、この条件がどういう条件なのかの実物である。**

**2 度目は `ddl_engine_version` 4 → 5（v2.9.33・2026-08-03）である** — `Instruction.thinness` を
末尾から `surface` の直前へ移し、**末尾を `surface` へ返した**。`ddl-engine-5/` も 33 ケースが
`ddl-engine-4/` とバイト一致で `changed_from_previous` は空。
**1 度目に学べなかったことがここにある** — 末尾へ移す判断は `thinness` の搬送（18% → 89%）だけを見ており、
**末尾を明け渡した `surface` が 92% → 42% へ落ちて Score 全体が半分に縮んだことは誰も測っていなかった**。
**宣言順を動かすときは、動かすフィールドだけでなく、席を譲る側も測る。**

**版木は戻せないが、刷りは残せる。** 凍結はそのための校正刷りである — 決まった入力から得た出力の
**実物**（SVG と、その要素数・class・座標の digest）を置き、既存ケースを再生成してバイト一致しなければ
CI が落ちる。一致しないときは描画が変わったということで、版を上げる。**版数は「変わった」という 1 ビット
しか運ばない。何がどう変わったかは、出力そのものを突き合わせないと分からない。**

## 版をめぐる原則

**版ごとの記録は下の各節にある。ここには版をまたいで効くものだけを置く。**
2026-07-28 に `SPEC.ja.md` §15.4〜15.12 から移した。

### 決定的な層と非決定的な層（v2.4.6）

**パイプラインは LLM の層と決定的な層が交互に並ぶ。** どこが再現し、どこが揺らぐかは層ごとに違う。
版を持てるのは決定的な層だけであり、この表がその線引きである。

| 層 | 実体 | 決定的か | LLM 呼び出し | 版 |
|---|---|---|---|---|
| 入力（記述） | 利用者が書くテキスト | — | — | `dh1`（記述同一性） |
| **Stage 1 解釈** | `interpreter.py` | **いいえ** | 19 箇所 | 版を持たない（`stage1_prompt_digest` で来歴のみ） |
| **プラグイン展開** | `plugins/document_format.py` の `expand_plugin_ddl` | **はい** | 0 | `ddl_engine_version` |
| **Stage 1.5 展開・変奏** | `ddl_expander.py` の `expand_intermediate_ddl` | **はい** | 0 | `ddl_engine_version` |
| **Stage 2 構成** | `composer.py` | **いいえ** | 19 箇所 | 版を持たない（`stage2_prompt_digest` で来歴のみ） |
| **coerce / validation** | `coerce/` の `coerce_score`（`normalize` = Score だけを見る補修 / `compose` = `ddl` を読んで構図を書く） | **はい** | 0 | `ddl_engine_version` |
| JSON Score | `schema.py` | — | — | `version`（`"0.1.0"`。Schema Version） |
| **Renderer 演奏** | `renderer.py` / `stroke_engine.py` | **はい**（seed 固定時） | 0 | `render_engine_version` |
| 出力（SVG） | 保存済み作品 | — | — | `rh3`（作品エディション） |

**決定的な層は隣り合っていない。** Stage 1.5（DDL→DDL）と coerce（Score→Score）のあいだに
Stage 2 の LLM が挟まる。したがって「DDL から Score まで」を 1 本の基準線にはできず、
決定的な区間ごとに別々のコーパスを持つ（本書の「参照コーパスによる世代比較」）。

**LLM の層に版を与えない理由**: 同じプロンプト・同じモデルでも出力は揺らぐ。
版数は「同じ版なら同じ結果」を含意するので、それが成り立たない層に置くと嘘になる。
代わりに送信したプロンプトの digest を作品ごとに記録し、**「入力条件が違った」は断定できるが
「出力が変わる」は主張しない**という弱い形にとどめる（裁定 ③-b）。

> `stage1_model` / `stage2_model` / `stage*_prompt_digest` は**依頼内容の記録**であり、
> 実行環境の記録ではない。同じ記録を持つ二つの作品が同じ Score になることは保証しない。
> これは欠陥ではなく、設計原則「揺らぎは仕様である」の帰結として受け入れる。

### 版と同一性 ID（v2.4.5）

**版と ID は名前空間が別である。** 数字が近くても連動しない。

| 名前 | 何の版か | 現在 | 上げる条件 |
|---|---|---|---|
| `render_engine_version` | 描画エンジン | `39` | **同一 Score + 同一 seed の演奏結果が変わるとき、または演奏できる語彙が増えたとき** |
| `ddl_engine_version` | 決定的変換層（展開・coerce・validator） | `20` | 同一入力 + 同一 seed の出力が変わるとき、**または `Instruction` のフィールド宣言順が変わるとき** |
| `ddl_version` | DDL 言語仕様そのもの（文法・キーワード） | `3` | **語彙の追加・変更・廃止、または文法の追加・変更・廃止**（2026-07-30 作者裁定で明文化。v2 は太さの語で、v3 は黄・橙・紫で上げた） |
| Score の `version` | JSON Score のスキーマ | `0.1.0` | スキーマの構造変更 |
| `MODEL_CONFIG_VERSION` | モデルカタログの中身 | `2.5.0` | **計測値・推奨度・選択可否が変わったとき**。上げると保存済みカタログの同じ id へ組み込みのメタを貼り直す（保存済みのモデル一覧と有効/無効の選択は残る） |
| `APP_VERSION` | アプリの版 | v2.13.47 | 採番のたび。**正本は `web/APP_VERSION` の 1 ファイル**で、UI・`/api/info` の `version`・CLI が同じ値を読む |
| `server/pyproject.toml` | 配布物の版 | 2.7.2 | **リリースのタグを打つときだけ**。`/api/info` の `release_version` が返す。リリース保留中はアプリの版から遅れる |
| `web/BUILD_NUMBER` | ビルド通し番号 | 973 | **UI の変更でも動く。ブランチごとの値ではなく共有の連番なので、番号は飛びうる。v2.9.23 以降は `.gitattributes` の merge driver が大きいほうを採るので、両側が採番しても競合しない**（`scripts/git/setup.sh` を clone ごとに 1 回） |

**「現在」の列は書いた時点の値である。** 版を上げたら、この列も同じ commit で直す。

**「演奏できる語彙が増えたとき」も版を上げる**（2026-07-25 作者裁定）。
新しい道具や新しい表面を足しても、**既存のコーパスはどのケースもその語を使っていないので
出力が 1 バイトも動かず、CI は落ちない**。結果が変わるときだけを条件にすると、
版を上げずに語彙を足せてしまい、「その語を演奏できる engine 12」と「できない engine 12」が
併存する。**同じ版なら同じ結果、という版数の意味が、結果ではなく入力の集合のほうで崩れる。**
語彙を足す版では、既存ケースがバイト一致することを確かめたうえで新しい版へ進み、
その一致自体を凍結物として残す。**版木を足しても既存の刷りが動いていないことの校正刷りになる。**

**道具や語の改名では版を上げない**（2026-07-27 作者裁定。v2.7.9 の先例を条文化した）。
`hair` → `silverpoint` のような改名は、**同じ入力から出る出力の文字列を動かす**ので、
上の「出力が変わるとき」に字義どおり当てはまってしまう。しかし**動いたのは名前だけで、
層の振る舞いは 1 mm も変わっていない** — 道具は同じ幅で同じ描き方をする。
版を上げると、**改名しかしていないのに世代の境界が来歴に入る**。

- **改名の版では、コーパスをその場で再凍結する**（新しい版のディレクトリを作らない）。
  render engine 15 と coerce ゴールデンは v2.7.9 でそうした。**DDL コーパスは
  同じ commit で取りこぼされ、CI が 8 回連続で赤になった**（v2.8.0 / Build 727 で解消）
- **同一性ガードは、版を上げない改名と凍結物の無断書き換えを区別できない。**
  ガードは書き込みの**後**に発火し、**1 回目に発火して 2 回目が exit 0 でバイト一致する**ことが、
  ガードの守りたい性質である。**発火を受け入れてよいのは、改名だと分かっているときに限る**
- **語彙が増えるときは上げる**（上記のとおり）。**増やすのと名前を替えるのは別である**

**`ddl_version` と `ddl_engine_version` は 1 から数え始める**（2026-07-24 作者裁定）。
他の版と数字が被らないため、別の名前空間であることが誤解されにくい。整数で刻む。

**作品エディション ID = `rh3`**（詳細は `SPEC.ja.md` §7 の render metadata 節）。
同一性は `score` + `render_seed` + render engine の ID と版 + `render_color_catalog_id` から決まる。

- **`render_build_number` は同一性に含めない。** build 番号は UI の変更でも採番されるため、
  **描画が 1 バイトも変わらないのにエディション ID が変わる**偽の差分を生んでいた。
  来歴としては保持する。「来歴として価値があり、同一性の定義に入れる価値がない」という切り分け
- **Score を作る側の seed（`vary_seed`）も含めない。** Score が違えば ID も違うので冗長である
- **`rh2` は legacy として保持し、再計算しない。** `rh2` と `rh3` は別の hash 空間であり、
  突き合わせて同一性を判定してはならない

### 参照コーパスによる世代比較（v2.4.4）

**決定的な層の各版には、同一入力から得た出力の実物を凍結した参照コーパスを一つ対応させる。**
版数は「変わった」という 1 ビットしか運ばない。**何がどう変わったかは、出力そのものを突き合わせないと分からない。**

- **既存ケースを再生成した結果はバイト一致しなければならない。** 一致しないなら、それは出力が変わったということであり、**該当層の版を上げる**
- **凍結済みの版は再生成して更新しない。** 新しい版のディレクトリを作る
- **ケース ID は永久に変えない。** 改名・削除は禁止で、追加のみを許す
- **コーパス同士を連結しない**（ある層のコーパスの出力を、別の層のコーパスの入力に使わない）。
  連結した瞬間に「どちらの層が変えたのか」を判定できなくなる
- コーパスの入力は、その層以外への依存を**すべて生成器側に literal で固定する**。色表も Score の全フィールドも書き下し、`COLOR_MAP` や schema の既定値を参照しない。出力が動いたのに manifest 先頭の識別子（`corpus_format_version` / `engine_version` / `schema_version` / `color_map_digest`）がどれも動いていないなら、**固定し損ねた依存が残っている**

現在の実体は 2 本ある（v2.6.0）。

| コーパス | 置き場 | 何を凍結するか | ケース数 |
|---|---|---|---|
| 描画 | `server/reference/render-engine-33/` | `renderer.py` / `stroke_engine.py` の演奏結果（SVG） | 586（SVG 4） |
| 決定的 DDL 層 | `server/reference/ddl-engine-18/` | **A** = `expand_intermediate_ddl` の展開後 DDL / **B** = `coerce_score` の補正後 Score + `branch_report` / **C** = `expand_plugin_ddl` の展開後 DDL + 単位数 + 断りの記録 + API へ渡す圧縮形（`score_instructions`） | 49（A 13 / B 30 / C 6） |

**DDL 側が A・B・C の 3 部に分かれるのは、決定的な層が隣り合っていないからである**（本書の「決定的な層と非決定的な層」）。
**C（プラグイン展開）は v2.13.1 で足した** —— この層は最初から版数を名乗っていたが、凍結出力を 1 度も持っていなかった。**A のプラグイン仕事は `ddl_expander` の `Nature.` マクロ正規表現**で、**文書プラグインの管理器を呼ぶのは render の経路だけ**だからである。
Stage 1.5（DDL→DDL）と coerce（Score→Score）のあいだに Stage 2 の LLM が挟まるため、
「DDL から Score まで」を 1 本の基準線にはできない。**A の出力を B の入力に使わない**のは
上記の「コーパス同士を連結しない」規律そのものである。

運用手順は成果物の隣（`server/reference/README.md`）に置き、再生成のバイト一致は
CI（`.github/workflows/reference-corpus.yml`）が層ごとに独立した job で強制する。
**採番の規律を「人が覚えているもの」から「機械的な制約」へ移すことが、この仕組みの目的である。**

**世代の比較はこう行う。** 版が上がるとき、新しいディレクトリを作り、前版の manifest と digest を突き合わせる。
動いたケース ID だけを `changed_from_previous` に列挙し、**そのケースの出力の実物だけを保存する**。
動かなかったケースは前の版のものがそのまま最新である。
「engine 12 でケース X はどう描かれるか」は、**最後に X が動いた版**を辿れば機械的に答えられる。

**ディレクトリの数が、そのまま「その層が何回変わったか」の記録になる。**

**この規律が実際に働いたのは engine 12 が最初である。** engine 11 はマスターグリッドの宣言で
全 220 件が動いたため、「動いた分だけ保存する」と「全部保存する」の区別がつかなかった。
engine 12 は 199 件を動かし、**21 件を動かさなかった**。動かなかったものの内訳が、
そのまま engine 12 が何をしたのかの説明になっている。

- **`rotring` の 12 件はバイト一致した。** 揺れ項がすべて 0 なので、脱・規則化が届く先を持たない。
  **道具語彙の機械の極は、engine 12 でも同じ位置にある**
- **`cloudform` の 9 件もバイト一致した。理由は別である。** 雲形は
  `generate_cloudform_contour` の Catmull-Rom パスとして書かれ、`stroke_engine` を通らない。
  したがって材質アウトライン層も持たない。輪郭自体は道具ごとに違う（10 道具の digest はすべて異なる）が、
  その違いはストローク合成に由来しない。**これは engine 12 が作った穴ではなく、engine 12 が露わにした穴である**

コーパスは配布物に含めない（`.gitattributes` の `server/reference/ export-ignore` により `git archive` から外れる）。

#### マスターグリッド（v2.4.8、engine 11）

**書き出す数値はすべて一つのグリッドに載る。** 小数 6 桁固定＝1000 単位キャンバスで
キャンバス比 **1e-9**。正本は `inku_server/master_grid.py` の `MASTER_GRID_DECIMALS`。

SVG は拡大自由だが、**書き出した数値そのものは固定小数**である。したがってこの定数が
実質的なマスター解像度になる。engine 10 までは書き出し箇所ごとに桁がばらついており
（`.1f` / `.2f` / `.3f` と、svgwrite へ素の float が渡って出る 17 桁）、
**同じキャンバスの上に 1e-4 から 1e-19 までの目盛りが同居していた**。

グリッドの値は上下から挟んで決めてある。

- **下限（再現性）:** プラットフォーム間の `math.sin` の差は相対 2e-16。実測では
  **小数 11 桁目から** macOS と Linux の出力が割れる。グリッドはそこから 4 桁上にあるので、
  どの OS で演奏しても同じ文字列が出る
- **上限（物理）:** 100m の壁へ引き伸ばしても刻みは 100nm。可視光の波長より細かく、
  描く手段の側が先に限界に達する

**末尾のゼロは詰めない。** 桁が固定なら成果物のどの数値も `-?\d+\.\d{6}` に一致し、
**グリッドに載っていることを出力そのものから機械検査できる**。詰めると
`695.45787` が 6 桁グリッドの産物か生の float かを見分けられず、
「丸めてから詰めた」という手順を信じる形になる。

**整数は整数のまま書かれる**（キャンバス寸法・`viewBox` など）。グリッドは小数を持つ値の規定である。

**このグリッドは形の忠実度とは別の軸である。** ストロークは曲線でなく直線の連なりとして
出力されており、実効的な形の解像度はキャンバス比 **2.2e-4**（弦の矢）にある。
桁のほうが 200 倍細かい。**壁面規模の出力で効くのは桁ではなく標本化のほうである。**

### エンジンは後戻りしない（版画としての実装、v2.4.6）

**過去の描画エンジンをシステムとして保持しない。版を選び直す機構も作らない。**

- **Replay は常に最新のエンジンで行う。** `current_render_engine()` は引数を取らず、版を選ばせない
- 記録された `render_engine_version` は**来歴**であって、再描画時の入力ではない
- **当時のエディションの再現は、保存済み SVG の返却で担保する。** 再描画では担保しない
- 再描画時、記録された版と現在の版が違うなら、**UI にその旨を表示するだけ**にとどめる
- DDL 側も同じ。再解釈は常に最新で行い、結果は新しいエディションになる

**これは版画と同じ構えである。**

> 彫りは進む。版木は一方向にしか変わらない。刷り上がった作品は残るが、**彫る前の版木には戻れない**。
> アプリケーション自体を一つの作品として考えるなら、この実装になる。

作品（保存済み SVG とその Score・seed・エディション ID）は**刷り**であり、そのまま残る。
エンジンは**版木**であり、彫り進めた先しか存在しない。
両者を混同して「過去の版木も倉庫に取っておく」ことをしないのが、この設計の選択である。

**その代償として、engine 1〜9 の出力は失われた。** コードも出力も残っていない。
参照コーパス（本書の「参照コーパスによる世代比較」）は engine 10 から始まる。
**だからこそ、現役のうちに刷りを取っておく。** コーパスとは、彫り進める前に取る**校正刷り**である。
版木は戻せないが、刷りは残せる。

**版数だけを記録して出力を残さないのは、彫った日付だけを書いて刷りを捨てるのに等しい。**


### PNG は演奏を写す（v2.7.10、v2.7.11）

**SVG が正本であり、PNG はそれを写した像である。** 像は縮んでよいし、粗くてよい。
**落としてはならない。**

#### 黙って落とすラスタライザを使わない

**PNG 化の経路に、SVG フィルタを実装せずに黙って飛ばす実装を置いてはならない。**
対象は少なくとも `feTurbulence` / `feDisplacementMap` / `feGaussianBlur` である。
これらは**地の粒と材質層の全部**を作っており、飛ばされた PNG は絵として成立してしまう。

**この規則は性能や画質の話ではなく、観測の話である。** 落とす実装を通した PNG は、
**「差が無い」と「差が写っていない」を区別できない**。inku では作品の採否・engine の版上げ・
移植の同一性が、いずれも**二枚の絵を並べて読む**ことで決まる。
写し損ねる道具を挟むと、**その判断すべてが静かに壊れる**。

#### `cairosvg` は使わない

**`cairosvg` は使用を禁じる**（2026-07-27 作者裁定、v2.7.10 で撤去）。
上の 3 フィルタをいずれも実装せず、**例外も警告も出さずに飛ばす**。
2026-07 のセッションで、これが焼いた「きれいに見える PNG」が **4 回、判断の材料にされかけた**。
警告は CLI の stderr・サーバーの起動ログ・docstring・成果物の `png_rasterizer` の四重にあった。
**それでも防げなかったのは、人を誤らせるのがログ行ではなく絵だからである。**
したがって**文書化ではなく撤去する**というのが、この節が定める扱いである。

#### 無い実装より、誤る実装のほうが悪い

**フォールバックを置かない。** 現在の唯一の実装は `resvg`（`resvg-py`）であり、
**それが無い環境では PNG 出力は静かに劣化するのではなく停止する**。
PNG が出ないことは目に見えるが、**質感の落ちた PNG が出ることは目に見えない**。

#### 守り方

`shared/src/inku_analysis/rasterizer.py` を**唯一の入口**とし、server・CLI・
Android 比較ハーネスのいずれもここを通す。番人は 3 つで、
**① 依存宣言に無いこと ② リポジトリのどの `.py` も import しないこと
③ 環境に入っていても到達不能であること**。

> **②の走査範囲は「どこを見るか」ではなく「どこを見ないか」で書く。**
> v2.7.10 では 4 つの根を名指ししたため `android/scripts/` を取りこぼした。
> **名指しの一覧は不完全になりうるが、不完全だと言うことはできない。**

### 配布（v2.4.0）

リリース版はコンテナイメージで配布する。git タグ `vX.Y.Z` の push を起点に GitHub Actions が `ghcr.io/oikawas/inku-api` / `ghcr.io/oikawas/inku-web` を multi-arch（amd64 / arm64）で build & push し、利用者は `deploy/` の compose と `.env.example` で起動する（Quickstart は `deploy/README.md`）。開発は従来どおり bare metal（rsync + systemd）で行い、コンテナは Release タイミングで更新する。標準プラグイン（`server/plugins/`、現在は Nature.leaves）はイメージに同梱される。

**アカウントの前提**: セルフサインアップの経路は設けない。アカウント作成は認証済み管理者による `POST /api/users` のみで、最初の入口は新規 DB 起動時に作られる bootstrap admin（`INKU_BOOTSTRAP_ADMIN_PASSWORD`、8 文字以上）である。この値が無いまま起動したサーバーは誰もログインできない箱になる（値を設定して再起動すれば復旧する。既存アカウントがある DB では何も起きない）。空文字は「未設定」として扱う（v2.4.0）。**v2.11.19 以降、この前提は単独利用モードを off にしたときのものである** —— `INKU_SINGLE_USER` を立てたサーバーは利用者を 1 人に定めて自動的にログイン済みにするので、bootstrap admin を要しない。**配布 compose は単独利用モードを既定 on とし、`INKU_BOOTSTRAP_ADMIN_PASSWORD` の必須チェックを外した** —— 「単独利用モードが off のときだけ必須」を compose の補間では表せないためで、off にする運用者が自分で値を設定する。

`/api/info` は版を 2 つ返す（v2.9.25 で分けた）。`version` は**アプリの版**で、`web/APP_VERSION` の 1 ファイルを読む — UI が画面に出す値と必ず一致する。`release_version` は**配布物の版**で、`server/pyproject.toml` を `importlib.metadata` から読む。**両者は別の概念で、リリースを保留している間は一致しない**（2026-08-01 実測でアプリ v2.9.24 に対し配布物 2.7.2）。分ける前は `version` が配布物の版だけを返しており、同じ画面に 2 つの版数が出ていた。

**デベロッパーモード（v2.4.3）**: 環境変数 `INKU_DEVELOPER_MODE` は、開発者向けの選択肢を画面に出すかどうかだけを決める。無効時は NVIDIA NIM が表示用モデルカタログ（`GET /api/models`、管理者のモデル設定、モデル一覧再取得）から外れ、Build 番号の常時表示（左下レール・ログイン画面・アプリ情報）も消える。**隠すのは表示だけで、実行経路・保存済みモデル設定・履歴のモデル情報・作品ごとの `render_build_number` は無効時も変わらない**（保存済み設定が非公開プロバイダーを指す場合、画面内の選択だけが公開カタログの先頭へ補正される）。配布 compose は既定で無効、開発・ベンチ用 compose は既定で有効。`/api/info` が `developer_mode` を返し、web はログイン前にこれを読む。

## engine 40 — non-computer の solid は走査線でなくむらを持つ base fill になる（v2.13.46）

**non-computer の `surface.texture="solid"` は、面積に比例して増える走査線をやめた。** 常に残る実体の base fill の上に、`baseFrequency=0.035`、`numOctaves=3`、alpha floor 0.31 の standard SVG filter によるむらを重ねる。filter seed と ID は render seed と instruction identity から決定的に導き、同じ Score・seed・profile は byte-identical のまま、同一 work 内でも filter ID は衝突しない。

**`display` と `editable` はこの標準 filter を持つ。** filter を読まない reader でも base fill は残る。`editable` は SVG-native editor 向けであり、部分対応 application を保証しない。**`compat` は filter / clipPath を追加せず、filter-free flat vector fallback の base fill を出す。** `computer × solid` は従来の周期的な一方向 scan と underlay を保ち、mottle へ移らない。

## engine 39 — 粒は面積へ散らさず、道具の痕を版として繰り返す（v2.13.45）

**`surface.texture="grain"` は閉図形の面積へ直接散布するのをやめ、固定寸法の `<pattern>` tile に有限の道具痕を置いて、閉輪郭を carrier path として反復参照する。** `density` は tile 内の論理粒数だけ、`scale` は粒の大きさだけ、`opacity` は pattern child だけ、seed は位置と jitter だけを決める。

**606 件のうち動いたのは grain を明示する 5 件だけで、残る 601 件は engine 38 と byte-identical である。** 対象は `C-display-surface-grain-pen`、`C-surface-grain-pen`、`C-surface-grain-pencil`、`E-wild-surface-grain-pen`、`E-wild-surface-grain-pencil`。`stipple`、`paper_grain`、`aquatint`、`wash`、`hatch`、`crosshatch`、`solid` はこの版で変わらない。

**4種類の道具 signature は tile の子要素にも残る。** carrier は `fill="url(#pattern)"` の閉輪郭であり、粒を generic circle に縮退させない。SVG profile 間で同じ grain 構造を使い、追加の `filter` / `clipPath` を必要としない。

## engine 38 — 線に付いた薄墨は、太くて淡い掃きである（v2.13.35）

## engine 36 — 薄墨は、縞ではなく面である（v2.13.27）

**面の 9 語のうち、`wash` だけが「面」と名乗りながら面になっていなかった。**
掃きは全部平行で間隔は一定、掃き 1 本の幅は間隔の 0.44〜0.74 倍しかなく、
**掃きと掃きのあいだにはどの層も届かなかった** —— 図形の中の **19.9%（四角）/ 21.1%（三角）** が
紙のまま残り、等間隔の縞に読めた。**薄墨に白地は無い。**

### 隙間を閉じるのは、掃きの太さだけだった

**前周に 14 段の梯子を測っている** —— 掃き 1 本ごとに角度を振っても、間隔をばらつかせても、
**白地の量は動かなかった**。動いたのは掃きを太くした段だけで、作者はそこから枡 `G3` を選んだ。
**幅を間隔の 0.88〜1.48 倍へ広げ、濃さの係数を 0.42 から 0.22 へ下げる。**

**動かしたのはこの 2 つだけである。** 間隔・層の数・層の角度は小数の末尾まで前の版と同じで、
下地も敷いていない（**退けられた 3 案は 1 つも入っていない**）。

### 隙間を埋めれば濃くなる。だから薄くする

**白地は 19.9% → 0.67%・21.1% → 1.09%** になり、**合成した濃さは +2.0% / +1.1%** に収まった。
**濃さを下げたのは好みの話ではなく、隙間を埋めた副作用を戻すためである** ——
掃きを 2 倍にしただけの段は、製品の 1.5〜1.9 倍の濃さになっていた。

**残った紙は輪郭際の縁で、深さの中央値は 2.0 / 2.2px** である。
掃きは輪郭で切られ（engine 35 の切り方が薄墨にも既に効いている）、手の筆は端で細るので、
いちばん外側の帯だけが薄い。**縞なら、間隔の幅の帯が図形を横切る。**

### 代償は、縁を倍またぐこと

**はみ出しは 12.3 / 11.0px から 25.8 / 21.7px になった。**
**これは掃き 1 本の幅の半分で、前の版でも同じ関係だった** —— 筆が幅を持つ以上、縁はその半分だけまたぐ。
粒の番人が使う絶対値 20.0px は**粒 1 つの大きさで決まった数字**なので薄墨には当てず、
薄墨の単位で「掃き 1 本のいちばん広い幅の半分」と言い直した。

### コーパスは増えず、6 件だけが動いた

**588 件のうち動いたのは、面の質感が `wash` の 6 件ちょうど。** 残り 582 件は前の版とバイト一致で、

## engine 24 — 薄れが、群の一人ひとりに届く（v2.11.6）

**「中心から縁へ薄れる」が、「全体がすこし淡い」として描かれていた。**

`Arrangement.fade` は群がどう落ちるかを宣言する — 中心から外へ（`outward`）か、
進む向きに沿って（`directional`）か。engine 23 まで、renderer はこれに**群ぜんぶで 1 つの定数**で答えていた。
`outward` に 0.40、`directional` に 0.48。**いちばん近い墨といちばん遠い墨に同じ数字が乗る。**
宣言は「落ちること」を述べているのに、描かれたのは「一様に淡いこと」だった。
**本番では 6,425 群のうち 2,738 群（42.6%）・178,694 痕のうち 83,703 痕がこれに当たる。**

**いまは一人ひとりが自分の上限を持つ。** `outward` は 0.62 → 0.18、`directional` は 0.70 → 0.26 へ
群の中の位置で傾斜する。**語彙もフィールドも足していない** — 宣言は最初からそこにあった。

**搬送路は `color_hint` である。** 色サイクルが hint を組み直したあとに札を書き、
**正規化が小数点を潰す前に読み戻す**。読む側が正規化後の値を見ると、**書いた傾斜がそこで平らになる。**

**配置と触れと演奏 seed は動いていない。** `color_hint` は `_SEED_INSTRUCTION_FIELDS` の外に居るので、
**薄れる群の経路座標は engine 23 とバイト一致し、変わるのは不透明度の属性だけである。**
面の seed も、instruction をハッシュする前に札を落とすので動かない。

**薄れられない群は、そのままにした。** 環は自分の中心から等距離であり、2 個の群も等距離である。
**順位をつければ、誰も述べていない濃淡が描かれてしまう。**

### 環は、重心から見ると等距離ではなかった

**この版で見つかった。** `_rhythm_t` は 0〜1 を**両端含み**で返すので、
**12 個の環は先頭と末尾が同じ点に重なる。** そのぶん重心が軸から**半径 / 個数**（実測 0.025）ずれる。
**重心から測ると環は等距離ではなくなり、環に一周する濃淡が出た。**

## engine 21 — 演奏が libm の最終桁を読むのをやめる（v2.9.34）

### 支持体と、道具ごとの受けやすさ

支持体は `stroke_engine` のモジュール定数（`Support`）として持つ。**`Score` のフィールドには足さない** —
`absorbency` は engine 15 で退役しており、その不在は検査で固定されている。

| weight | absorb | tooth |
|---|---:|---:|
| brush_thin / brush_thick | 1.00 | 0.15 |
| crayon / pencil / chalk | 0.10 | 1.00 |
| pen | 0.15 | 0.15 |
| silverpoint | 0.05 | 0.25 |
| drypoint | 0.00 | 0.35 |
| burin | 0.00 | 0.10 |
| **rotring / computer** | **0.00** | **0.00** |

**機械に紙との接触は無い。** ただし 2 つの機械が不変である理由は同じではない —
`computer` は `stroke_engine` を通ったうえで bias 0 が守っており、**`rotring` はそもそも合成へ入らない**
（`_uses_hand_stroke` が engine 8 から除外している）。**表の 0 は記述であって機構ではない。**

強さは 4 段（g0〜g3）を実装し、**採択は g2**（滲み amp 0.70 / span 0.16 / rate 1.5、
掠れ depth 0.88 / span 0.07 / rate 1.5、墨を切る閾値は包絡 0.55）。
他の段は**単調性を検査できる形で残してある**。

### 掠れは、墨の本体を切る

**幅を細めるだけでは見えない。** 弾かれるべき道具がちょうど最も細い道具（pencil 1.5px / chalk 3px /
crayon 4px）なので、0.25 倍にしても 520px ラスタで 0.20〜0.52px にしかならずアンチエイリアスに沈む。
**掠れは「墨がつかない＝白が残る」現象であって「線が細くなる」ことではない。**

包絡が閾値を超えたサンプルでは墨を置かず、そこでストロークを切る。
**SVG の 1 個の `path` は subpath を複数持てる**（`ring_path` が既にそうしている）ので、
**切っても要素は 1 つも増えない**。これは engine 15 の前例（繊維 38 本で地が絵全体の 46% を占めた）への
恒久的な歯止めであり、**要素数が 1 つでも増えたら不合格**である。
**閉じた輪郭は even-odd の帯を保つため切らない。**

### 揺らいだ直線も、同じ地に出会う

位置に `variation` を持つ直線は、renderer が**揺らいだ中心線のまわりに outline を作り直す**別の経路を通る
（`outline_for_centerline`）。**切れ目をここへ持ち越さないと、幅の応答だけが残って墨が切れない** —
バイトは動くので凍結コーパスでは「動いた」と数えられ、**見える側の半分だけが黙って落ちる**。

- 実測（pencil・seed 20260731・直線 5 本）: 持ち越さないと **variation なし 10 subpath /
  variation あり 5 subpath**（切れ目ゼロ）
- **弧は `variation` の有無に関わらず切れる。** この差は直線だけのものである
- 到達は**保存 1858 作品のうち 912 件 = 49.1%**、うち弾かれる道具で描かれたものが **242 件 = 13.0%**

切れ目は `StrokeResult` に載って `outline_for_centerline` へ渡り、**直線の分岐と同じサンプルで両岸を割る**。

> **この経路を検査する図柄に弧を混ぜてはならない。** 弧は揺らぎの有無に関わらず切れるので、
> **直線の切れ目が 1 つも無くても subpath が増え、検査が自分の言い分を自分で供給する。**

**契約の満点 381/493 は、実装では 227/493 になった。** 参照実装が g0 以外の段で直線ストロークの outline を
頂点ごとの法線で作り直しており、**抵抗の bias を全部 0 にしても 177/493 が動いた** ＝
**381 のうち 46% は地の抵抗と無関係**だった。本実装は固定法線のままにしてある。

**未裁定**: 材質輪郭は切れ目をまたいで描かれ続ける。墨が切れた白地の上を材質輪郭の破線が渡る。
切るなら polyline を path へ変える必要があり、コーパスの材質輪郭が全件動く。

## engine 18 — 十三のカタログが、九色ぜんぶを持つ（v2.9.14）

**engine 17 は palette から選ぶ経路を作った。本版は、選ばれる先の表そのものを入れ替える。**
**動かしたのはデータだけである** — 解決連鎖・帯の定義・無彩のしきい値・seed の材料はすべて
engine 17 のままで、`renderer.py` に差分は無い。

**engine 17 の表は帯を持たないカタログが多かった。** 記述が緑を求めても緑が無ければ最近傍の
黄が代役に立つ。保存済み 7463 instruction を通すと、**記述が求めた帯をカタログが持たない事例が
140 件**あった。

- **13 本がそれぞれ palette 10 色**を持ち、内訳は**無彩ちょうど 3・有彩ちょうど 7**に固定される。

- **`map` は 6 キーから 9 キーへ**広がり、**9 キーすべてがその本の palette の中から選ばれる**
  （従来は `map` と palette が別々の色を持てた）
- **色見本は `map` の派生で、有彩 6 キーが先頭**である — Android が `swatches.take(4)` と
  `take(8)` で 2 つの画面に描くので、無彩が先頭に来るとその枠を黒・灰・白が占める
- **130 色は全カタログを横断しても 1 つも重複しない**
- **`desert_mineral` を退役させ、`moss_bark` / `neon_plate` / `lantern_dew` を足した。**
  退役したのは無彩が 1 色しかないカタログで、engine 17 の潰れ防止規則はこれのために在った
- **退役した 10 の id は `get_color_catalog` も `render_color_map_for_catalog` も `None` を返す**
  （`default` へ落とさない）。本番の 117 作品がこの id を記録しているが、**保存済みの migration は
  行っていない** — 未知 id は従来どおり既定カタログで描かれる

## engine 17 — カタログの palette が絵へ届く（v2.9.12）

**8 色の名前つき palette は、これまで `color_hint` の文字列照合でしか描画へ届いていなかった。**
記述チャネルはほぼ空である — 保存済み 7463 instruction のうち、Stage 2 が書いたセグメントに
色語を含むものは **945 件（12.7%）** しかない。**87% の instruction には照合する相手が無く**、
`cmap[color]` ＝ カタログの `map` 6 色（と v2.9.11 が足した 3 既定色）で終わっていた。

**本版は palette から決定的に選ぶ経路を作る。** 割当は**作品ごとに 1 回だけ**計算し、材料は
**`(render_seed, catalog_id, 抽象色)` の 3 つだけ**である。instruction の全 dump は使わない
（使うと `color_hint` を書き換えるだけで色が変わり、A/B が交絡する）。`performance_seed` も使わない —
**色は演奏ではなく作品の性質**だからである。

- **有彩 6 語**は OKLCh の色相帯で分類する（赤 345–50° / 橙 50–80° / 黄 80–137° / 緑 137–200° /
  青 200–280° / 紫 280–345°）。**CIELAB は使えない** — 純青 306° と純マゼンタ 328° が隣り合い、
  青と紫を分離できない。帯の候補が複数なら seed で 1 つ、0 なら帯中心に最も近い有彩 palette 色、
  palette に有彩が 1 色も無ければ `map` 値へ落ちる
- **無彩 3 役**は、`map` 値と同じ hex の候補を**先に予約**してから、残りを `map` 値の L に近い順で取る。
  素朴な「L 最大 / 最小 / 中間」では、**無彩の palette 色が 3 つ未満のカタログ 5 つで白と黒が同じ hex になる**
  （`desert_mineral` は無彩が 1 色しかない）
- **背景も同じ割当を通る**
- **`catalog_id` を renderer へ通した** — それまで `renderer.py` に `catalog_id` は 1 件も出現していなかった。
  `api.py` の 2 呼び出し・`RenderEngine.render()`・`DefaultRenderEngine`・`render()` の 4 ファイルである。
  省略時は `DEFAULT_COLOR_CATALOG_ID` として扱う
- **`_hint_hues` を単語境界照合へ変えた**（ASCII のみ。CJK は語境界が無いので文字一致のまま）。
  **語として成立しない 5 トークンを語彙表から落とした** — `blu` / `ai`（青）・`vert` / `tall`（緑）・`shu`（赤）。
  `vertical` 166 件・`constraint` 20 件・`blur` 13 件の誤起動がこれで止まる。**真正なフランス語 `vert` も
  読めなくなる**が、誤起動を止める側を採った。`brown` は帯を持たないので `orange` へ送る

**動いた 110 / 不変 365。不変の側が本版の境界そのものである** — 6 キーの `map` だけを渡され、
`palette:` キーも `color_hint` も持たず、背景が `white` の呼び出しは engine 16 と 1 バイトも変わらない。
**既存の 365 ケースはすべてその形だった**（`palette:` キー 0・`color_hint` 0 件・instruction の色は
`black` 364 と `green` 1 の 2 語だけ・背景は全件 `white`）ので、**ケース表を拡張しなければ 1 件も動かなかった。**
F 群 110 件を足した — 11 カタログ × 9 抽象色の 99 件、記述 6 件、非白背景 5 件である。

保存済み 1847 作品 / 7463 instruction を、**v2.9.9 が診断文を `note` へ移した後の面**（保存済みの
`color_hint` から診断セグメントを外したもの）で測った。

|---|---|---|

| 実描画の無彩 | 57.9% | **61.4%** |

**本版は彩りを増やさない。無彩は増える。** 帯を決めるのは抽象色であり、保存済み作品の抽象色は
**69.5% が無彩**だからである。**本版が動かすのは「どの palette 色が使われるか」であって、帯の比率ではない。**

### 紙に溶ける 8 役（本版では直していない）

**白地との明度差 ΔL が 0.15 未満の役は、engine 16 の 0 / 88 から engine 17 で 8 / 88 になった。**

- **`render_engine_version` 16 → 17**
- **`ddl_engine_version` は 4 のまま・`ddl_version` は 3 のまま** — DDL の語彙も文法も動かない
- **参照コーパス `render-engine-17/`** — 475 件（A 88 / B 72 / C 58 / D 28 / E 119 / **F 110**）、

  `DEFAULT_COLOR_MAP` 一枚の digest で、**`renderer.COLOR_MAP` を変えても動かなかった**
  （v2.9.11 の 3 語追加も digest 不変で通った）。F 群はケースごとに違う `color_map` を持つので、
  **475 ケースすべての `(case_id, catalog_id, color_map)` 集合の digest** とした

  再演奏して manifest の digest と突き合わせるテスト**を足した

## engine 16 — 面を痕跡にし、太さを軸にする（v2.9.3）

**3 つの変更を 1 つの版にまとめた。** engine 15 と同じ理由で、どれも同じ層に属し、
版を 3 回上げれば Android の追随が 3 回要る。

- **面は塗るのでなく演奏する** — 8 つのてざわり語のうち 6 つは、bbox に一様乱数で撒いた円だった
- **微小な塗りは置く** — 走査線が引けない小ささの塗りは、領域 fill へ縮退していた
- **太さは道具名から独立した軸になる** — `thinness`（`fine` / `extra_fine`）

**動いた 333 / 不変 32。不変の 32 件は全部 `rotring` と `computer`。**
engine 12 の 12 件・engine 15 の 32 件に続いて、**3 版連続で同じ側に立っている**。
文法がすべてゼロで種を消費しないので、**手を変える軸は、手を持たない道具に届かない**。
`C-tinyfill-circle-rotring` の 1 件は二重に不変で、マニフェスト上この 1 件だけが class を 1 つも持たない。

詳細: `server/reference/README.md` の "What engine 16 changed" ／
[CHANGELOG v2.9.3](../../CHANGELOG.ja.md)

### 面は、輪郭の内側で演奏される

`stipple` / `grain` / `paper_grain` / `aquatint` / `wash` / `bleed` の 6 語は、
**図形の外接矩形に一様乱数で円を撒いていた。図形そのものを一度も見ていない。**

| 図形 | 粒が図形の外に落ちていた割合（engine 15） | engine 16 |
|---|---|---|
| 三角 | **46 / 90（51%）** | **0** |
| 雲形 | **43 / 90（48%）** | **0** |
| 多角形 | 20 / 90（22%） | **0** |
| 円 | 12 / 90（13%） | **0** |

**三角形に「粒を撒く」と書くと、半分は三角形の外に落ちていた。**
engine 16 は輪郭の内側へ位置を決め、粒 1 つを 1 筆として演奏する。
走査は `_render_fill_strokes` と同じ `_scanline_segments` を使うので、凹形（雲形）もそのまま扱える。

`bleed` だけは機構が違う。engine 15 は **bbox 中心の楕円 1 個**で、図形が何であれ同じ絵だった。
engine 16 は輪郭を外へ押し出した帯 3 重で、押し出し量は頂点ごとに揺れる。
**最内輪は輪郭の上（オフセット 0）に置く** — 滲みは縁の両側に起こるものなので、
帯が図形から離れた所に浮かない。

`hatch` / `crosshatch` の 2 語は**1 バイトも変えていない**。この 2 つは engine 15 の時点で
既に中心線を `synthesize_along` へ通しており、面を撒いていなかった。**この 8 件が不変であることが、
本節の変更が「撒いていた 6 語だけ」に閉じていることの担保になる。**

#### 同じ語が、プロファイルごとに無関係な 2 つの絵になっていた

engine 15 の display は `feTurbulence` + `feDisplacementMap` + `feGaussianBlur` をかけた**矩形**を出し、
editable は円を撒いていた。**同じ `wash` という語が、見る場所によって別の絵だった。**

engine 16 は両プロファイルとも同じ機構で描く。残るプロファイル差は他の層と同じ
**材質フィルタの有無だけ**である。**display の clipPath も廃止した** —
粒が輪郭の内側から引かれるので不要であり、**`bleed` は外へ染み出すので clip はむしろ描いたものを消す**。

**速度は 1.44 倍になった**（面を持つ本番作品 119 件・display で 56.2 s → 80.9 s）。
90 個の円を 90 本の合成ストロークに置き換えたぶんで、機構どおりの増分である。

### 微小な塗りは、走査するのでなく置く

塗りが小さすぎて走査線が引けないとき、engine 15 は**領域 fill へ縮退**していた。
**縮退は失敗を防いでいたのであって、正しかったわけではない** — 手の道具で塗った小さな図形が、
そこだけ機械の塗りになっていた。

engine 16 は 1 筆の打点として置く。図形の長い方の軸に沿って運び、幅は短い方の軸が決める。

- **機構が切り替わる境界は、短辺がキャンバスの約 3%**（実測 2.9〜3.2%。道具 5 種・seed 6 種で確認し、
  **切り替わりは 1 度きりで行きつ戻りつしない**）
- **運びの下限 0.90 を実測で選んだ。** 0.30 では `_edge_window` が両端の 16% ずつで幅を 0 まで落とすため、
  **10px の塗り円が「輪郭だけになって内部が空く」**。1.10 では打点が図形より濃くなる（墨量 115%）
- **`rotring` は `_uses_hand_stroke` の手前で分岐する**ので、どの大きさでも領域 fill のままである

本番の手の道具の `filled` 閉図形のうち **75.3% が打点へ回る**（150 作品の実測）。

### 太さは揺らぎではなく寸法である

**太さは道具名の性質だった。** 細い線を求めることは別の道具を求めることであり、
「細いペン」は書けなかった。engine 16 は `Instruction` に `thinness` を置く。

| 道具 | 既定 | `fine` | `extra_fine` |
|---|---|---|---|
| silverpoint | 0.5 | 0.5 | 0.5 |
| rotring | 1.0 | 0.6 | 0.5 |
| pencil | 1.5 | 0.9 | 0.525 |
| pen / computer | 2.0 | 1.2 | 0.7 |
| drypoint | 2.6 | 1.56 | 0.91 |
| chalk / brush_thin | 3.0 | 1.8 | 1.05 |
| burin | 3.2 | 1.92 | 1.12 |
| crayon | 4.0 | 2.4 | 1.4 |
| brush_thick | 8.0 | 4.8 | 2.8 |

**下限は新しい数ではなく、最も細い道具そのものである**（`MIN_STROKE_WIDTH = WEIGHT_TO_STROKE_WIDTH["silverpoint"]`）。
「銀筆より細い線は引けない」と読める。**銀筆は太さの指定を受け付けない。これは仕様であって欠落ではない。**

**倍率は 3 案を実際に描いて墨の被覆率で選んだ。**

- **退けた 0.7 / 0.45** — **太筆の `fine` が既定の 99%** で、描いても変わらない。
  太筆は材質層の絶対幅成分が大きいので、墨だけ 30% 細めても絵が動かない
- **退けた 0.5 / 0.25** — **道具の区別が潰れる。** `extra_fine` で 5 つの道具が下限に張り付き、
  **11 道具の相異なる幅が 9 → 6 に落ちる。太さの軸が道具の軸を食う**
- **採った 0.6 / 0.35** — `extra_fine` で相異なる幅は 9 → 8（銀筆とロットリングだけが合流する）。

`base_width` を公称幅に据え置くと**墨だけが細って材質が取り残される**。

**coerce が添える線には `thinness` を付けない。** 添景は coerce の声であって記述者の要求ではないため、
**記述された細さは、記述者が書いた図形にだけ乗る**。

## engine 14 — 一枚の方眼と、暴れるの到達（v2.7.0）

- **量子化された格子を、作品ごとに 1 枚に統一した**
- **「暴れる」を輪郭・弧・塗り・ハッチへ届かせた** — engine 12 では線プリミティブにしか届いておらず、
  **説明と実装が食い違っていた**（円や四角は ON でも出力がバイト一致していた）

**動いた 126 / 不変 221。** コーパスは 228 → 347 件へ増えた（暴れるの新規ケース）。

詳細: [CHANGELOG v2.7.0](../history/changelog-v1.72-v2.4.ja.md)

**engine 13 が残した 2 つの穴を、演奏結果が変わる 1 つの版として塞いだ。**
どちらも出力が動くので、まとめて 1 つの版にしてコーパスの再凍結を 1 回で済ませている。

### 方眼は紙の性質であって、置かれた対象の性質ではない

engine 13 の格子は目盛が**ストローク長に比例**していた（`step = 長さ × 0.018`）。その結果、

- **長さの違うものは目盛が違う**（100px → 1.8px、400px → 7.2px、800px → 14.4px）
- **同じ長さでも置かれた位置で位相が変わる**。同一長の線を 30 箇所に置くと **30 種すべて異なる図**になった
- 1 枚の絵の中に**大きさの数だけ別々の方眼**が同居していた

engine 14 では目盛を **`キャンバス短辺 × quantize`** で決める。`quantize` の値は `0.018` のままだが、
**意味が「ストローク長に対する比」から「キャンバス短辺に対する比」へ変わった**。
`stroke_engine` はキャンバスを知らないので、**renderer が px へ直して `grid_step` として渡す**。
長さ相対の経路は残していない（切り替えフラグも既定値も置かない）。

- 正方 1000px で **18.000000px**。短辺基準なので**アスペクトで変わる**（a4 12.726px / oban 12.006px /
  vertical 10.116px / **pillar 3.600px**）。これは帰結であって不具合ではない
- **同じ絵の中のすべてのストロークが同じセルへ落ちる。** 被覆セルの一辺は 1 つの Score で単一の値になり、
  中心は同じ目盛の整数倍に乗る（大小 3 対象を同居させた実測で、格子から外れた座標が 188/194 → **0/194**）
- **方眼が対象の大きさで縮まなくなったので、連続する標本が同じセルへ丸め込まれることが起きる。**
  重なったセルは重ねて描く（一意化しない）。作者はこの見えを含めて 18px を選んでいる

### 暴れるが輪郭へ届く

engine 12 の「暴れる」は **`line` プリミティブにしか届いていなかった**。実測では
**11 道具 × 8 プリミティブ 88 組のうち 63 組が ON/OFF でバイト一致**しており、
`SPEC.ja.md` §13.4 の「作品全体に一つのトグル」という位置づけとずれていた。

engine 14 では `synthesize_along`（円・楕円・三角・四角・多角形・弧・塗り・ハッチ）にも
中心線ジェスチャを足し、`wild` を通す。**OFF の出力は 1 バイトも変わらない**（既存 228 件のうち
OFF で動いたのは格子の変更による 7 件だけである）。

**バイト一致してよいのは 25 組だけで、それぞれ理由が違う。**

| 一致してよい組 | 件数 | 理由 |
|---|---|---|
| 全 11 道具 × `cloudform` | 11 | `cloudform.py` が `stroke_engine` を通らない（**engine 14 でも直していない既知の穴**） |
| `rotring` × 残り 7 プリミティブ | 7 | 道具文法の `gesture` が 0。機械の極 |
| `computer` × 残り 7 プリミティブ | 7 | `periodic` が `WILD_GAIN` を飛ばす（本書の「engine 13」） |

### 素朴な移植では壊れる 3 点

直線のジェスチャをそのまま輪郭へ写すと破綻する。**いずれも試作で実測して仕様に落とした。**

1. **弧長で振幅を決めてはならない。** 閉輪郭の周長は寸法ではない（多角形が星形になった）。
   **閉輪郭は `周長 / τ`＝半径相当で測る**
2. **ジェスチャの平均を差し引く。** 平均が 0 でないと図形全体が伸縮する（円が一回り縮んだ）。
   **大きさは楽譜が決めるものであって、演奏が変えてよいものではない**
3. **角（anchor）の手前で窓を 0 へ落とす。** 意図へ戻される頂点の隣にジェスチャが乗るとトゲが出る

### 材質は墨に追随する

輪郭と弧の材質アウトライン（`class="material-outline"`）は**幾何から引かれていて、
演奏された中心線を見ていなかった**。暴れるを届かせると **9 組すべてで墨だけが動き、材質が幾何の上に
取り残された**。これは engine 12 が直したのと同じ型の不具合である（材質層が中心線に追随せず、
独立した罫線として背景に残る）。

**暴れる ON のときは、輪郭・弧の材質アウトラインと粉を演奏後の中心線から作る。**
OFF のときは engine 13 のままである。

`render_engine_version` は `13` → **`14`**。参照コーパスは **347 件**（`corpus_format_version` は
`"1"` → `"2"`。ケースの入力に `wild` が加わったため）。`changed_from_previous` は **126 件**で、
内訳は**既存 7 件**（`A-computer-*` から `cloudform` を除いたもの）と**新規 E 群 119 件**（暴れる ON の
全数 88 + 塗り 15 + 面 16）、**不変 221 件**である。**手の 10 道具は 1 件も動いていない。**

## engine 13 — コンピュータのてざわり（v2.6.0）

- **道具に「コンピュータ」を足した。** 幅と経路が固定の刻みに落ちる。**誤差なく反復する**のが核
- 反復は seed でばらつかない。材質層は直線で、dash は全数が同じ値

**動いた 8 / 不変 220。動いた 8 件は新しく足したコンピュータのケースそのもの**で、
**既存の 220 件は 1 件も動いていない。** 道具を 1 つ足しても既存の演奏を動かさなかった、という記録である。

詳細: [CHANGELOG v2.6.0](../history/changelog-v1.72-v2.4.ja.md)

**11 番目の道具「コンピュータ」を足した。** 核は「手が震えない」ではなく **「誤差なく反復する」**。
手は同じ値を二度出せない。計算機は同じ値しか出せない。**周期＝線に沿った方向の反復、
格子＝空間方向の反復**で、同じ性質の 2 軸である。

`rotring` との区別はここで立つ。**rotring は反復すべき揺れを持たない**（道具文法が全項 0）。
**コンピュータは揺れを持ち、それを正確に繰り返す。** したがって engine 11 の対称エンベロープへの
後戻りではない。engine 11 のそれは**選べない既定**であり、engine 13 のこれは**選べる語彙**である（本書の「エンジンは後戻りしない」と衝突しない）。

- **反復は seed でばらつかない。** 機械の周期（energy の 5 周期 + 10 周期、gesture の 2 周期）も
  幅の段も格子も定数で、`render_seed` を引数に取らない。**同じ Score なら seed を変えても
  出力はバイト一致する**（手の道具は一致しない）。ただし**配置と運動語彙の seed 依存は上の層の話**なので従来どおり残る
- **「暴れる」は効かない**（`SPEC.ja.md` §13.4）。暴れは手の話であり、`rotring` と同型に扱う
- **格子**: 中心線の座標を格子へ丸め、幅を 4 段に落とす。**engine 13 の刻みは `ストローク長 × 0.018` で、
  対象ごとに別の方眼になっていた。engine 14 で `キャンバス短辺 × 0.018` の 1 枚の方眼へ改めた**（本書の「engine 14」）
- **閉じた輪郭はロットリングとほぼ同じでよい。** 閉輪郭専用の半径変調は作らない。それが CG のテイストである

### 材質は「標本化の残り」である

手の道具の材質層は**道具が線の脇に落とすもの**である（黒鉛の粉、筆の毛、蝋の削れ）。
計算機にはそれがない。**あるのは、格子へ丸めるときに捨てた差である。**

**幾何が「誤差なく反復する」。材質が「誤差を捨てた跡」を見せる。**

標本ごとに、丸める前の位置と丸めた後の位置の差（残差）を取り、**残差が 0 でない標本にだけ**
格子 1 セルの正方形（`class="raster-bleed"`）をストロークの下に敷く。セルは**格子に丸めた座標**に置き、
濃さは**残差の大きさに比例**する（セル半分ずれたときに上限 0.45）。seed を使わないので、
**同じ図なら同じ跡が出る**。

**端点は意図へ固定され、多角形の角は anchor で意図へ戻される**ので、それらの標本は残差を持たず
セルを出さない。直線は 41 標本のうち 39、四角は 80 のうち 76、弧は 62 のうち 60 がセルになる。

**この材質は engine 13 の第 1 版から作り直している。** 最初の版は「まっすぐな定規の線 + 全数同一の
等間隔 dash」だった（旧作 `rh2:9e991c…` の「直線の雨」を道具の性質として置き直す設計）。
実装して目視すると、**材質層が意図した始点→終点に固定される一方、演奏された中心線は最大 55px 離れる**ため、
点線が線から切り離されて独立した罫線に見えた。**絵画上の意味を持たないので捨てた。**

## この文書の作り方

- **一覧の数値は手で書かない。** `server/reference/render-engine-*/manifest.json` の
  `changed_from_previous` と、その版のディレクトリに置かれた SVG の枚数から取る
- **版を上げたら、この文書に 1 節足す。** 節には必ず**不変の側**を書く
- **日英 2 版がある。** `render-engine-history.ja.md` が正本で、英語版はそれに従う。
  `server/scripts/check_docs.py` が見出しの対応を検査する
