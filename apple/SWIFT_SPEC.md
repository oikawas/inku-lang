# inku Swift Implementation Specification

This directory contains the native SwiftUI client, developed for macOS first, and the shared Apple packages. [SWIFT_SPEC.ja.md](SWIFT_SPEC.ja.md) is the canonical specification for Swift host behavior; this document is its maintained English version. The [product specification](../SPEC.md) defines shared DDL, Score, prompts, authoring authority, pipeline transitions, seeds, and rendering semantics. Server remains the primary development host, and Swift follows the same Rust core without duplicating semantic processing.

Last updated: 2026-10-18.

Binding and protocol identities come from the bundled Rust core's version report; rendering layer identities use render metadata and the [Server layer definitions](../server/src/inku_server/layer_versions.py). Do not duplicate shared engine version constants in this document. The macOS app has its own version, defined by `apple/VERSION` and `apple/BUILD_NUMBER` and allocated separately from the Server and Web versions (the first release is 1.0.0, Build 1). The corresponding Server version is shown in the app's About inku window and in the changelog. Matching shared layer versions does not establish that host features and the native UI port are complete.

Work identities `dh1`/`rh3`, canonical JSON, instruction-language normalization and resolution, and description-label text and excluded spans call the shared core through UniFFI. Swift keeps no copies of these rules and only converts the core's Unicode scalar offsets to the macOS editor's UTF-16 offsets. Existing stored identities are not rewritten. `ExactJSON.text` preserves number lexemes for transport, `canonicalText` exposes the core's canonical form, and the space-separated prompt format `pythonText` remains separate.

Options and replacements for Change the touches, Change the ground and Change the color arrangement also call UniFFI's `saved_variants` (`inku.saved-variants.v1`). Swift supplies the saved parent's conditions and a fresh random UInt64 each time the touches button is pressed. Ground sentences use the saved instruction language, or the core's shared language rule when absent. Child metadata keeps the core's answer; color metadata contains only `color_arrangement_index` and `catalog_id`. Color indices and totals retain the core's decimal representation without truncation to UInt64. Refusals display the core's `detail` unchanged. No migration rewrites existing works or their saved metadata (2026-10-17).

## Specification Update Workflow

- `SWIFT_SPEC.ja.md` is the canonical Swift specification.
- Update the Japanese specification first, then synchronize `SWIFT_SPEC.md` as a translation or adaptation that preserves its intent. Do not add English-only requirements.
- Record confirmed implementation changes and remaining scope in dated sections of this specification. Maintain product history in the shared [CHANGELOG.ja.md](../CHANGELOG.ja.md) and [CHANGELOG.md](../CHANGELOG.md). Do not create a separate Swift changelog.
- Update the relevant canonical document when shared semantics or persistence contracts change. This document explains how the Swift host applies them; it does not establish an independent shared specification.
- Public documentation describes source and reproducible procedures. Generated binaries, models, logs, credentials, device identifiers, and private operating records are not tracked product material.

## 2026-10-18 Library page numbers, typed page numbers, and the work search in the history strip

## 2026-10-18 Open the Library at the shown work

Switching thumbnails and list keeps the timeline's first work (it used to move to a page boundary).

This applies to grid cards, lineage cards and rows, and a lineage's picture in the list; a row of the list table opens with a double click (and Return). Nothing opens from the trash.

## 2026-10-18 Lighter Library page turns

One page turn rebuilt the SwiftUI tree of the Library's 56 cards three times and decoded 56 thumbnails at once (the author's instruction about slow Library paging). Without changing looks, wording or operations:

- Page capacity: when taller cards reduce the capacity within the same viewport, the first work stays in place and the works that no longer fit start the next page, as Web `setPageSize` does. Neither the page nor the lineage beneath it is read again. Only then do pages begin elsewhere than at the newest work (Web `startOffset`): ← Newer reaches the works before the kept one and Latest returns to the newest. A new viewport (window size, preview opened or closed), a filter or a view change counts from the start as before.
- Cards: a card receives the values it shows (work, label, comment, generation, selection, current work, enabled states, model lines) and is rebuilt only when they change. Work menus are assembled when opened. Menu states and saved display labels are read with the page and shown in the same update as the works. Keyboard focus belongs to the reused card slot; Return and Space act on the work that slot shows. Only small views such as the pager read the loading flag.
- Tooltips: the AppKit part that locates the bubble is placed when the pointer or keyboard focus arrives, and kept only for a control disabled from outside, which needs it to notice the pointer. A focus binding is attached only to text inputs, and to controls while Full Keyboard Access is on. The bubble's look, text, placement and timing are unchanged.
- Thumbnails: at most four decodes for the screen run at once. A read is stopped once no view waits for it, as when a card changes to another work. Finished images are published together at most every 50 ms. After a page is shown, the next page's stored PNGs are decoded into memory at low priority (at most two at a time, after the screen's reads) without pushing out the works on screen. The memory limit grows from 96 MiB to 160 MiB (two pages of 512px images of about 1 MB each, plus the history strip and the lineage).
- Lineage: lineage revision marks and comments are read from the lineage snapshots. Before, turning Library pages made the revision marks of lineage works absent from that page look off. Labels, lock marks and refinement menu headings are read by small views inside lineage cards, so reading a Library page does not rebuild them.
- Measurement: AppCheck `--library-paging-perf-only` (a disposable database of 600 works with stored PNGs, a window never shown, a lineage beneath). At 2172×1010 (56 per page) the median main-thread CPU time of one turn went from 416 ms to 207 ms, card rebuilds from 168 to 56, NSViews from 3486 to 2358, concurrent decodes from 54 to 4, and memory hits on opening the second page from 0/56 to 56/56. At 2172×960 (the third page shrinks from 56 to 42) that turn's reads went from 2 to 1 and lineage reads from 1 to 0. A connected AX client could not be reproduced in process and was not measured (SwiftUI builds no AX tree without a client). The NSViews that remain are AppKit `.borderless` buttons and `Menu`s, with the drawing views SwiftUI splits around them, kept so that nothing looks different.
- Checks: AppCheck `--library-pagination-only` (adds the first work kept by a shrink and the lineage keeping a comment across pages) and `--thumbnail-memory-only` (adds the four-decode limit, a later viewer after an abandoned read, and a prefetch that leaves the works on screen). How tooltips appear and keyboard operation of cards are left to the author's on-screen check.

## 2026-10-17 Move the ChatGPT plan's next-action table to the shared core

For a ChatGPT plan failure, the next action shown (retry, reconnect, consent, settings, models, edit, usage, diagnose) and whether the pipeline may retry (`provider_rejected`, `transport_unavailable`, `transport_timeout`) come from UniFFI `provider_wire`'s `chatgpt_failure`. The shared core's [`provider_wire/chatgpt.rs`](../core/crates/inku-pipeline/src/provider_wire/chatgpt.rs) holds the table, and Server and Android use the same one. Requested by the Server session (shared Rust, step 5).

- `ChatGPTPlanDiagnostic` no longer keeps its own list of temporary codes or its next-action table; it passes the code, and whether the failure is temporary only when the core classified it, to `chatgpt_failure`. A code outside the table is `provider_rejected` with "diagnose". When the core classifies a stream or HTTP failure itself, its answer's `failure` and `action` are used as they are.
- Whether the pipeline retries is the table's `failure`, never derived from the next action. Codes such as `chatgpt_cancelled` show "retry" but stay `provider_rejected`, so the pipeline does not retry them on its own.
- Seven codes Swift raises change their next action: `chatgpt_attempt_busy` (diagnose to retry), `chatgpt_auth_rejected` (diagnose to reconnect), `chatgpt_cancelled` (diagnose to retry), `chatgpt_consent_declined` (diagnose to consent), `chatgpt_registration_incomplete` (diagnose to reconnect), `chatgpt_session_changed` (reconnect to retry) and `chatgpt_session_stale` (diagnose to reconnect). No code changes whether the pipeline retries.
- The core now checks the stream's response ID and the function call's ID, and drops model list rows it cannot publish and repeated slugs (the differences from old Swift reported in step 4). Swift needs no change for these.
- Checks: all 162 rows of the shared fixture's `chatgpt` section (16 requests, 57 streams, 9 failures, 5 lists, 75 `chatgpt_failure`) are read through the core itself and through the Swift receivers. The test that refuses differing response IDs, removed in step 4, is back.

## 2026-10-17 Move ChatGPT plan bodies and stream reading to the shared core

The ChatGPT plan's drawing and Vision request bodies, the reading of its SSE stream, HTTP failure classification and the model list call UniFFI's `provider_wire` (`inku.provider-wire.v1`) actions `chatgpt_request`, `chatgpt_vision_request`, `chatgpt_limits`, `chatgpt_stream`, `chatgpt_error` and `chatgpt_catalog`. The shared core's [`provider_wire/chatgpt.rs`](../core/crates/inku-pipeline/src/provider_wire/chatgpt.rs) is authoritative, and Server and Android read with the same rules. Requested by the Server session (shared Rust, step 4).

- Swift's `ChatGPTResponseDecoder` is gone; the receiver is [`ChatGPTWire.swift`](Packages/InkuHost/Sources/InkuHost/ChatGPTWire.swift). The drawing body passes the effect's prompt as its original JSON, and the core's body string is sent unchanged and written to the observation record.
- The stream is still received whole and read once. While receiving, the host holds only the whole-stream limit the core returns (`wire_limit`); the core checks the per-event and answer limits as it reads. The last `response` goes to the observation record. Tool-shape diagnostics log only the shapes the core returns, never text or arguments.
- Whether a failure is temporary (retried) follows the core's classification (author's decision). The next action shown still comes from Swift's table. An item that did not complete, and a summary whose status is not `completed`, are now refused instead of retried (as on Server). A stream that ends before completion and `response.incomplete` are still retried.
- A malformed stream (an event that is not JSON, bytes that are not UTF-8 and so on) is `chatgpt_response_invalid`. An event that was not JSON used to stop with the internal code `invalid_json`.
- Two shapes only Swift refused are no longer refused, as on Server: `response.created` without a `response`, and response IDs that differ between `response.created` and `response.completed`. Vision images follow the core's data URL check, so an untyped `data:;base64,…` is sent.
- The model list uses the core's answer as is (author's decision). Duplicate slugs and empty names are kept, and a row that is not an object makes the whole list unreadable (`chatgpt_response_invalid`). HTTP failure bodies also read `param` under `response.error` and the code of a body shaped `type: "error"`.
- Tokens, the registration store, locks, cancellation, timeouts, the pause on a usage limit and the observation record are unchanged.
- Checks: a new test reads all 69 rows of the shared fixture's `chatgpt` section (8 requests, 8 Vision, 42 streams, 9 failures, 2 lists) through the core itself and through the Swift receivers. Tests that drove the old decoder directly now read whole streams. The old Swift differed on 23 of the 69 rows; the step 4 RESULT keeps the breakdown.

## 2026-10-16 Single-user alignment with Server

The single-work PNG UI flag follows Web: enabled preserves transparency; disabled composites white. Migrate old UI preferences once, inspecting raw field presence before filling defaults and distinguishing an existing file with an omitted field from a new installation. Do not convert saved works, saved export options, or execution journals. Clipboard images have a white background. Do not propagate this flag into cards, animation, or native multi-work PNG contracts. Enumerate PNG choices from saved templates.

Persist a local client fanout limit, default 4 and integer range 1–16, rejecting invalid values. Capture it at run start; changes affect the next run. Do not add a Server-wide worker limit. New demo UI edits accept 1–999 seconds while previously saved 1000–3600-second values survive reading, starting, and unchanged saving.

Calculate library page capacity by summing each row's measured maximum height without rounding fractional geometry. When taller cards reduce the capacity within the same viewport, keep the first work in place and move the works that no longer fit to the next page, as Web `setPageSize` does (2026-10-18). Project display labels from saved provenance, including original batch line numbers, once per page. Do not invent missing labels. Different runs may share a label; selection, actions, and copying use UUIDs. Canvas search beside Lineage is independent of library search: case-insensitive exact UUID, description substring, and hash prefix/suffix/full matching. Searching updates the history strip without switching the displayed work; selecting a result opens it.

Layout's single option and next four, and tool change's next four, save every checked unsaved candidate before replacing the set. Partial failure preserves remaining candidates and selection and does not save successes twice. Separate this operation from save-and-close (Server SPEC 2026-10-17). Generation information copies the saved work's UUID with brief success feedback, invalidated when its target changes.

The new automatic backup schedule accepts 1–365 days, 1–100 generations, and a local time. Its deadline is the last automatic backup's local date plus the interval at that time. A first run is immediately due; manual backups do not advance the automatic deadline. Preserve the legacy hourly schedule until the user saves the new schedule. Reading or migrating settings never prunes generations. Prune only owned automatic generations after a successful automatic backup. The app cannot run backups while closed. Do not apply Server application-log deletion, rotation, or compression to work/execution JSON.

Show common Web content, order, and copy first, retaining system theme and native default format/profile as macOS supplements. Preserve the local database, Keychain, native panels/bookmarks, Finder/OS sharing, OS menus/shortcuts, lineage detail refinement menu, all batch rows, and explicit unknown-outcome handling. Generate bundled catalog/UI references from a fixed clean source SHA and preserve user model names, purposes, and availability overrides. These are implementation requirements, not evidence of completed builds, device verification, or author acceptance.

## 2026-10-15 Library pagination

Chronological and grouped library pages follow Web/Server by omitting SVG text and displaying persisted PNG thumbnails. Size labels retain the saved SVG's UTF-8 byte count. A missing or stale PNG reads only its work's SVG to rebuild it. Opening in Create or lineage, refining, and exporting read the complete saved record by the chosen work ID. Thumbnail task identity does not contain SVG text. Recording card heights alone does not rebuild the whole library. Paging leaves the background lineage alone; explicit refreshes and work mutations still update it.

Menu eligibility reads only saved origin and authority for the page and publishes the results together, without loading each card's entire instructions, Score, and rendering context. It checks the same required objects, strings, and work ID as the full context reader. Missing or invalid records do not become eligible.

Card slots, buttons, and menus are reused within a page. An image appears only when its rendered work ID and hash match the current work; expanded descriptions reset by work ID. Checks and action targets follow saved work IDs rather than carrying the previous page's state.

As in Web's `HistoryThumbnail.svelte`, individual images show no loading animation. Presentation reads the existing 96 MiB bounded decoded-PNG cache synchronously, keeping visited images visible without waiting for a task. Unread images show a quiet background while loading asynchronously. Synchronous lookup performs no SQLite read, PNG decoding, or rendering; 512px images, work/hash identity, LRU limits, and orphan removal remain in effect. Focused check: AppCheck `--thumbnail-memory-only`.

## 2026-10-15 Library preview, search, and history strip

The work preview follows the order of image, opening hint, full description, lineage/refinement/export actions, work-information table, and comment. Double-clicking the image or activating it from the keyboard opens that work in Create; inspection alone does not replace the Create draft. Closing and reopening the same preview retains an unsaved comment without mixing another work's information. Details show save time, stage models (one row when equal), catalog, canvas, seconds, SVG size, render version, generation, and a short hash with full-hash copy. Export first selects a format, then opens settings for that work.

Search follows Web's description/hash/work-ID label, hint, and inline clear action. Clearing retains input focus. Existing description, DDL, model, and catalog searches remain, with hash prefixes and whole/prefix work IDs added. History-strip model names use Web's word abbreviations while retaining versions, sizes, variants, and quantization. Long names wrap in smaller text. Saved names can use the catalog when a connection is absent without registering or enabling a drawing model.

The native export mark, filter, and work attribute that stood in for sharing are removed; they did not represent Server sharing permissions. The Swift physical schema v4 [migration](Packages/InkuPersistence/Sources/InkuPersistence/Resources/migration-v4.sql) removes only `library_annotations.for_share`, preserving comments, revision marks, works, lineage, and executions. The [Swift schema export](../persistence/reference/swift-schema-v4.json) records its authority. Known v1-v3 databases migrate; older backups migrate in an isolated snapshot before restoration. Older binaries cannot open v4 databases: rolling back requires the pre-migration backup together with the old code. File export remains available.

## 2026-10-15 Work shown at startup

As on Web, startup reads normal saved works in descending save-time order and opens the first work. Trashed and lineage-only works are excluded; the previous selected work ID does not determine the choice. Its image, instructions, description, and saved information come from that work's record. If no normal work exists, the canvas stays empty. This selection happens once during initialization; New and history refreshes do not reopen a saved work automatically. Startup does not redraw, call an LLM, or save history.

## 2026-10-15 Batch tab

The batch heading, hint, text font and spacing, three empty-input examples with line numbers, count, and input history follow Web. Dragging the input's bottom-right corner changes its height. History uses a scrolling list capped at half the window height and names each input by its first line. Choosing one restores only the input and closes the list. Next conditions order model, catalog, Sketch from life, Wild, canvas, and New together; native seed details sit behind the heading's ellipsis. During a run, disabled condition fields show the captured starting values without changing settings for the next batch.

The resume card shows an interrupted badge, original next line, remaining and completed counts, and explains that it restores original input and conditions while skipping completed works. During a run, the compact current line precedes disabled next conditions and a single progress and stop block. ## 2026-10-05 Batch connection-loss handling and failure diagnostics

The drawing pipeline creates an HTTP client for each core-owned attempt, matching Server. Terminal failures use the same execution's failed event and the corresponding action's final metric to save the processing stage, safe cause, attempt number, and diagnostic code in the row error. If the final metric succeeded but core validation failed, an earlier retry's connection loss is not reused as the cause.

Connection-loss records alone cannot establish the disconnection source or whether session reuse caused it. This change addresses the client-lifetime difference and missing diagnostics. Shared-core prompts, schemas, finite retries/fallback, and result identities stay unchanged.

Private execution `ProviderAttemptObservation` records may contain bodies; ordinary history, prompt panels, and result logs cannot expose them. Raw data is fetched only when the developer explicitly opens its disclosure. Refresh records reloads a record opened while a request was running. Request and response bodies each have a 16MiB limit. Interrupted, oversized, and cancelled replies retain incomplete/truncated facts and cannot be presented as complete records. Swift limits the aggregate body UTF-8 bytes of one execution to 64MiB and reserves 16MiB response headroom before sending. Overflow prevents sending; older records are never evicted or silently omitted. This is a body-byte budget, not a bound on the entire encoded snapshot or app memory. Endpoint URLs, headers, credentials, connection settings, and exception text are excluded; echoed known credentials are also removed. The screen previews the first 32KiB, and sharing the full stored body requires an explicit developer action. Ordinary metric APIs return no raw bodies, and raw reads are rejected outside developer mode.

### Executions, providers, and cancellation

[PipelineHost](Packages/InkuHost/Sources/InkuHost/PipelineHost.swift) uses a driver for each execution to serialize core mutations and persistence. Prompts, schemas, retry decisions, documents, and authoring authority retain their core-defined semantics. Swift performs the requested transport and persistence effects. Core snapshots are stored as opaque owned bytes.

Provider adapters support OpenAI-compatible services, the MLX API profile, Anthropic, and Gemini. The current settings view stores one endpoint and one model shared by Stage1 and Stage2. Ordinary settings live in `providers.json` beside the DB; API keys live in separate Keychain items. Saving connection settings does not send an LLM request. Sending requests to real providers and accepting individual models require separate checks.

A pending claim is persisted before a provider request starts, and a response from an obsolete request cannot update state after cancellation. Cancellation reaches the transport task and the shared core's cancel command. The app model waits for stopping to finish before starting another generation. Swift's JSON boundary preserves integer lexemes and does not round UInt64 seeds through `Double`.

Restoring a saved execution is read-only and never automatically repeats an interrupted provider request. The explicit resume API completes durable local effects only; it does not restart provider work. Executions with a pending provider claim refuse resume. User-facing recovery controls for this API are not connected yet.

### Storage, reading, and saved Score replay

Storage semantics follow the [portable persistence contract](../persistence/README.md), [contract.json](../persistence/contract.json), and [logical projection v2](../persistence/reference/logical-projection-v2.sql). Swift has an independent physical schema v1, defined by its [bundled SQL](Packages/InkuPersistence/Sources/InkuPersistence/Resources/schema-v1.sql), [schema export](../persistence/reference/swift-schema-v1.json), and [record mapping](Packages/InkuPersistence/Sources/InkuPersistence/Records.swift). Its physical schema version is not interchangeable with the portable contract or other hosts' schema versions.

`ddl` is the only instruction body used for saving, display, editing, and replay. Optional `ddl_source_origin` records adoption of a legacy body; it is neither a second body nor authoring authority. NULL versus empty strings, unknown states/fallbacks and JSON fields, and original whitespace and line endings are preserved. When `source_text` is NULL, readers can display `input` without changing the stored value. Seeds are decimal TEXT; `at` is Unix epoch milliseconds.

One `InkuDatabase` actor and a GRDB `DatabaseQueue` own the writer. Existing DBs undergo read-only schema validation before a writer opens. Unknown, future, or partial schemas are refused. Only new DBs are created with the current schema, and there is no destructive fallback. Swift does not directly open Server or Android databases, and macOS/iOS do not share a live DB file.

A work, its lineage node, and an optional edge are saved in one transaction. History primary-key collisions are refused; render hashes are not unique. `commitEffect` atomically commits the next snapshot/storage revision, ACK, and optional work/lineage records. A success ACK is returned only after the DB commit. Retrying an identical effect does not duplicate a save; different contents or a stale storage revision cause a conflict. Storage revisions are distinct from document authority revisions.

Selecting or reading a saved work uses its stored DDL, Score, and canonical SVG without compiling or rendering again. Explicit replay validates the saved Score and its attested policies, clip, and options, invokes the shared `renderSaved` boundary, and saves a new work and lineage child. It does not rewrite the source work or invent policies for a work without rendering context. The current UI replays with the saved options.

### Backup and restore

Manual backup uses the SQLite Backup API to capture a consistent snapshot including WAL contents. After schema, integrity, and stored-value validation, a standalone SQLite file is published at a new destination. Existing backups are not overwritten. Copying only the DB file is not treated as a backup.

Restore cannot start from the UI during generation. It stops host executions, keeps the original backup read-only, validates an isolated snapshot, and replaces the active DB through the Backup API. After success, the app model resets execution, selection, and display state and reloads works. Content's restoration revision closes library preview, discards Demo/Batch observations and temporary Creation/presentation snapshots, and rereads library state, generations, and the selection position from the restored DB. DB backups include works, lineage, executions, snapshots, and ACKs; adjacent provider JSON and Keychain credentials are excluded.

Automatic backup generations are handled by the local maintenance feature above. FTS and import of legacy Server/Android databases or legacy JSON are not implemented. The legacy-body selection helper using the fixed Unicode whitespace set does not establish a complete import feature.

### Raster and native display

The [shared raster crate](../core/crates/inku-svg-raster/Cargo.toml) renders SVG and returns owned premultiplied RGBA8 with width, height, stride, and pixel format. Swift mechanically converts this to an sRGB `CGImage` and retains the pixels for the image's lifetime. The display path does not omit filters or medium effects. Raster requests obey shared SVG size, dimension, and pixel limits and do not obtain resources from external networks or filesystems.

The [ArtworkRenderer](Sources/InkuUI/ArtworkRenderer.swift) actor maintains a bounded cache keyed by SVG digest, raster API version, requested dimensions, and color space. The saijiki preview requests rasters when needed for display. Since 2026-10-06 the work area is drawn by `DisplayRenderer` (Skia) and thumbnails read the PNGs baked and kept (the dated sections above). Current PNG export rasterizes the saved SVG at height 1024; SVG export writes the saved canonical SVG unchanged. This does not implement the full custom-size or animated export specification.

### Initial macOS UI and disconnected features

A `NavigationSplitView` rail provides creation, library, lineage, and settings views. Creation binds description/direct DDL, language, shared catalog/canvas, seed, and wild settings to the app model. The initial input is English direct DDL that can run without a model connection. Generation/cancellation, saved-work selection and replay, read-only DDL/Score, canvas zoom/pan, recent works, library search, provider settings, SVG/PNG export, image copy, and manual backup/restore are connected.

Library and recent works show normal, nontrashed records and disable selection during processing. Search operates on loaded works; it is not whole-DB FTS or a pagination UI. Works with an empty source use the display title "無題" without changing their stored source.

Remaining M3 features include the lineage graph, favorite/trash controls, plugin/model advice dialogs, batch/demo, custom and animated exports, and share cards. The lineage view explicitly reports that it is disconnected. Unimplemented features do not appear as successful actions. The iPad/iPhone app, camera, sharing, device lifecycle handling, and real-device acceptance remain future work.

### Build and verification boundaries

See [README.md](README.md) for clean-clone tools, pinned dependencies, resource generation, generators, artifacts, and execution commands. [build-macos.sh](scripts/build-macos.sh) defaults to release Rust and a Release app; debug can be selected explicitly. It builds the Xcode project generated from [project.yml](project.yml) using a generic Mac destination, both architectures, and `ONLY_ACTIVE_ARCH=NO`. This is an unsigned local build. Signing, notarization, and distribution are separate work. Generated bindings, XCFrameworks, resources, the project, and build outputs are reproducible artifacts.

Bounded checks confirmed Mac arm64/x86_64 Rust artifacts and Swift linking, plus a Universal macOS app build. On Apple Silicon, direct DDL produced Score/SVG, SQLite storage survived app-model recreation, owned rasters displayed natively, and canonical saved SVG export succeeded. Initial native views also displayed the generated work and recent thumbnail, selected library works, and created new history through saved Score replay. UInt64 seed preservation, pixel ownership, input errors, and persistence boundaries are checked through small cases tied to concrete failures.

iOS device/simulator Rust artifacts were generated, but iOS app builds, signing, and real-device acceptance are incomplete. Intel hardware startup/performance, real provider requests, and author acceptance of routine use and full functionality require separate checks. CLI checks, Universal builds, native-view checks, and real-device acceptance do not substitute for one another. Select verification according to the concrete failure a change prevents.

The app's `--database` argument selects a temporary DB for isolated trials. It changes the DB and adjacent provider JSON destination, while Keychain storage remains independent. README contains the concrete commands for normal use and isolated trials.
