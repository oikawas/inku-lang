# render engine の版史

**演奏（描画）の版だけを、新しい順に 1 版 1 節で並べた索引である。**
inku は同じ JSON Score から毎回わずかに違う絵を出す。**その「出し方」の版が render engine 版**で、
製品の版数（`v2.7.8` など）とは別に数える。**この文書はどの版で何が変わったかを引くための入口**であり、
詳細は各節が指す先にある。

**この文書が新設されるまで、1 つの版から 15 までを通して見られる場所はどこにも無かった。**
記録は 4 箇所に散っていた（2026-07-28 に本書へ集約した） — 英語 `SPEC.md` の散文（engine 5〜10）、日本語 `SPEC.ja.md` §15.9〜15.11（13〜15）、
`server/reference/README.md`（12 と 15）、そして CHANGELOG の版エントリ。

## 版を上げる条件

下の「版と同一性 ID」が定める。**2 つある。**

1. **同じ Score と同じ seed から出る演奏結果が変わったとき**
2. **演奏できる語彙が増えたとき**（描画が 1 バイトも変わらなくても上げる）

**改名では上げない。** 逆に、**上げたら参照コーパスを凍結する** — その版が動かしたケースの SVG だけを
`server/reference/render-engine-<版>/` に置き、manifest が全ケースの digest を持つ。

**版木は戻せないが、刷りは残せる。** 凍結はそのための校正刷りである — 決まった入力から得た出力の
**実物**（SVG と、その要素数・class・座標の digest）を置き、既存ケースを再生成してバイト一致しなければ
CI が落ちる。一致しないときは描画が変わったということで、版を上げる。**版数は「変わった」という 1 ビット
しか運ばない。何がどう変わったかは、出力そのものを突き合わせないと分からない。**

## 版をめぐる原則

**版ごとの記録は下の各節にある。ここには版をまたいで効くものだけを置く。**
2026-07-28 に `SPEC.ja.md` §15.4〜15.12 から移した。

### 決定的な層と非決定的な層（v2.4.6）

**パイプラインは LLM の層と決定的な層が交互に並ぶ。** どこが再現し、どこが揺らぐかは層ごとに違う。
版を持てるのは決定的な層だけであり、この表がその線引きである。

| 層 | 実体 | 決定的か | LLM 呼び出し | 版 |
|---|---|---|---|---|
| 入力（記述） | 利用者が書くテキスト | — | — | `dh1`（記述同一性） |
| **Stage 1 解釈** | `interpreter.py` | **いいえ** | 19 箇所 | 版を持たない（`stage1_prompt_digest` で来歴のみ） |
| **プラグイン展開** | `plugins/document_format.py` の `expand_plugin_ddl` | **はい** | 0 | `ddl_engine_version` |
| **Stage 1.5 展開・変奏** | `ddl_expander.py` の `expand_intermediate_ddl` | **はい** | 0 | `ddl_engine_version` |
| **Stage 2 構成** | `composer.py` | **いいえ** | 19 箇所 | 版を持たない（`stage2_prompt_digest` で来歴のみ） |
| **coerce / validation** | `coerce/` の `coerce_score`（`normalize` = Score だけを見る補修 / `compose` = `ddl` を読んで構図を書く） | **はい** | 0 | `ddl_engine_version` |
| JSON Score | `schema.py` | — | — | `version`（`"0.1.0"`。Schema Version） |
| **Renderer 演奏** | `renderer.py` / `stroke_engine.py` | **はい**（seed 固定時） | 0 | `render_engine_version` |
| 出力（SVG） | 保存済み作品 | — | — | `rh3`（作品エディション） |

**決定的な層は隣り合っていない。** Stage 1.5（DDL→DDL）と coerce（Score→Score）のあいだに
Stage 2 の LLM が挟まる。したがって「DDL から Score まで」を 1 本の基準線にはできず、
決定的な区間ごとに別々のコーパスを持つ（本書の「参照コーパスによる世代比較」）。

**LLM の層に版を与えない理由**: 同じプロンプト・同じモデルでも出力は揺らぐ。
版数は「同じ版なら同じ結果」を含意するので、それが成り立たない層に置くと嘘になる。
代わりに送信したプロンプトの digest を作品ごとに記録し、**「入力条件が違った」は断定できるが
「出力が変わる」は主張しない**という弱い形にとどめる（裁定 ③-b）。

> `stage1_model` / `stage2_model` / `stage*_prompt_digest` は**依頼内容の記録**であり、
> 実行環境の記録ではない。同じ記録を持つ二つの作品が同じ Score になることは保証しない。
> これは欠陥ではなく、設計原則「揺らぎは仕様である」の帰結として受け入れる。

### 版と同一性 ID（v2.4.5）

**版と ID は名前空間が別である。** 数字が近くても連動しない。

| 名前 | 何の版か | 現在 | 上げる条件 |
|---|---|---|---|
| `render_engine_version` | 描画エンジン | `14` | **同一 Score + 同一 seed の演奏結果が変わるとき、または演奏できる語彙が増えたとき** |
| `ddl_engine_version` | 決定的変換層（展開・coerce・validator） | `1` | 同一入力 + 同一 seed の出力が変わるとき |
| `ddl_version` | DDL 言語仕様そのもの（文法・キーワード） | `1` | 文法の追加・変更・廃止 |
| Score の `version` | JSON Score のスキーマ | `0.1.0` | スキーマの構造変更 |
| `APP_VERSION` / `server/pyproject.toml` | 製品リリース | v2.5.0 | リリースごと |
| `web/BUILD_NUMBER` | ビルド通し番号 | 706 | **UI の変更でも動く** |

**「演奏できる語彙が増えたとき」も版を上げる**（2026-07-25 作者裁定）。
新しい道具や新しい表面を足しても、**既存のコーパスはどのケースもその語を使っていないので
出力が 1 バイトも動かず、CI は落ちない**。結果が変わるときだけを条件にすると、
版を上げずに語彙を足せてしまい、「その語を演奏できる engine 12」と「できない engine 12」が
併存する。**同じ版なら同じ結果、という版数の意味が、結果ではなく入力の集合のほうで崩れる。**
語彙を足す版では、既存ケースがバイト一致することを確かめたうえで新しい版へ進み、
その一致自体を凍結物として残す。**版木を足しても既存の刷りが動いていないことの校正刷りになる。**

**道具や語の改名では版を上げない**（2026-07-27 作者裁定。v2.7.9 の先例を条文化した）。
`hair` → `silverpoint` のような改名は、**同じ入力から出る出力の文字列を動かす**ので、
上の「出力が変わるとき」に字義どおり当てはまってしまう。しかし**動いたのは名前だけで、
層の振る舞いは 1 mm も変わっていない** — 道具は同じ幅で同じ描き方をする。
版を上げると、**改名しかしていないのに世代の境界が来歴に入る**。

- **改名の版では、コーパスをその場で再凍結する**（新しい版のディレクトリを作らない）。
  render engine 15 と coerce ゴールデンは v2.7.9 でそうした。**DDL コーパスは
  同じ commit で取りこぼされ、CI が 8 回連続で赤になった**（v2.8.0 / Build 727 で解消）
- **同一性ガードは、版を上げない改名と凍結物の無断書き換えを区別できない。**
  ガードは書き込みの**後**に発火し、**1 回目に発火して 2 回目が exit 0 でバイト一致する**ことが、
  ガードの守りたい性質である。**発火を受け入れてよいのは、改名だと分かっているときに限る**
- **語彙が増えるときは上げる**（上記のとおり）。**増やすのと名前を替えるのは別である**

**`ddl_version` と `ddl_engine_version` は 1 から数え始める**（2026-07-24 作者裁定）。
他の版と数字が被らないため、別の名前空間であることが誤解されにくい。整数で刻む。

**作品エディション ID = `rh3`**（詳細は `SPEC.ja.md` §7 の render metadata 節）。
同一性は `score` + `render_seed` + render engine の ID と版 + `render_color_catalog_id` から決まる。

- **`render_build_number` は同一性に含めない。** build 番号は UI の変更でも採番されるため、
  **描画が 1 バイトも変わらないのにエディション ID が変わる**偽の差分を生んでいた。
  来歴としては保持する。「来歴として価値があり、同一性の定義に入れる価値がない」という切り分け
- **Score を作る側の seed（`vary_seed`）も含めない。** Score が違えば ID も違うので冗長である
- **`rh2` は legacy として保持し、再計算しない。** `rh2` と `rh3` は別の hash 空間であり、
  突き合わせて同一性を判定してはならない

### 参照コーパスによる世代比較（v2.4.4）

**決定的な層の各版には、同一入力から得た出力の実物を凍結した参照コーパスを一つ対応させる。**
版数は「変わった」という 1 ビットしか運ばない。**何がどう変わったかは、出力そのものを突き合わせないと分からない。**

- **既存ケースを再生成した結果はバイト一致しなければならない。** 一致しないなら、それは出力が変わったということであり、**該当層の版を上げる**
- **凍結済みの版は再生成して更新しない。** 新しい版のディレクトリを作る
- **ケース ID は永久に変えない。** 改名・削除は禁止で、追加のみを許す
- **コーパス同士を連結しない**（ある層のコーパスの出力を、別の層のコーパスの入力に使わない）。
  連結した瞬間に「どちらの層が変えたのか」を判定できなくなる
- コーパスの入力は、その層以外への依存を**すべて生成器側に literal で固定する**。色表も Score の全フィールドも書き下し、`COLOR_MAP` や schema の既定値を参照しない。出力が動いたのに manifest 先頭の識別子（`corpus_format_version` / `engine_version` / `schema_version` / `color_map_digest`）がどれも動いていないなら、**固定し損ねた依存が残っている**

現在の実体は 2 本ある（v2.6.0）。

| コーパス | 置き場 | 何を凍結するか | ケース数 |
|---|---|---|---|
| 描画 | `server/reference/render-engine-14/` | `renderer.py` / `stroke_engine.py` の演奏結果（SVG） | 347 |
| 決定的 DDL 層 | `server/reference/ddl-engine-1/` | **A** = `expand_intermediate_ddl` の展開後 DDL / **B** = `coerce_score` の補正後 Score + `branch_report` | 29（A 15 / B 14） |

**DDL 側が A と B の 2 部に分かれるのは、決定的な層が隣り合っていないからである**（本書の「決定的な層と非決定的な層」）。
Stage 1.5（DDL→DDL）と coerce（Score→Score）のあいだに Stage 2 の LLM が挟まるため、
「DDL から Score まで」を 1 本の基準線にはできない。**A の出力を B の入力に使わない**のは
上記の「コーパス同士を連結しない」規律そのものである。

運用手順は成果物の隣（`server/reference/README.md`）に置き、再生成のバイト一致は
CI（`.github/workflows/reference-corpus.yml`）が層ごとに独立した job で強制する。
**採番の規律を「人が覚えているもの」から「機械的な制約」へ移すことが、この仕組みの目的である。**

**世代の比較はこう行う。** 版が上がるとき、新しいディレクトリを作り、前版の manifest と digest を突き合わせる。
動いたケース ID だけを `changed_from_previous` に列挙し、**そのケースの出力の実物だけを保存する**。
動かなかったケースは前の版のものがそのまま最新である。
「engine 12 でケース X はどう描かれるか」は、**最後に X が動いた版**を辿れば機械的に答えられる。

**ディレクトリの数が、そのまま「その層が何回変わったか」の記録になる。**

**この規律が実際に働いたのは engine 12 が最初である。** engine 11 はマスターグリッドの宣言で
全 220 件が動いたため、「動いた分だけ保存する」と「全部保存する」の区別がつかなかった。
engine 12 は 199 件を動かし、**21 件を動かさなかった**。動かなかったものの内訳が、
そのまま engine 12 が何をしたのかの説明になっている。

- **`rotring` の 12 件はバイト一致した。** 揺れ項がすべて 0 なので、脱・規則化が届く先を持たない。
  **道具語彙の機械の極は、engine 12 でも同じ位置にある**
- **`cloudform` の 9 件もバイト一致した。理由は別である。** 雲形は
  `generate_cloudform_contour` の Catmull-Rom パスとして書かれ、`stroke_engine` を通らない。
  したがって材質アウトライン層も持たない。輪郭自体は道具ごとに違う（10 道具の digest はすべて異なる）が、
  その違いはストローク合成に由来しない。**これは engine 12 が作った穴ではなく、engine 12 が露わにした穴である**

コーパスは配布物に含めない（`.gitattributes` の `server/reference/ export-ignore` により `git archive` から外れる）。

#### マスターグリッド（v2.4.8、engine 11）

**書き出す数値はすべて一つのグリッドに載る。** 小数 6 桁固定＝1000 単位キャンバスで
キャンバス比 **1e-9**。正本は `inku_server/master_grid.py` の `MASTER_GRID_DECIMALS`。

SVG は拡大自由だが、**書き出した数値そのものは固定小数**である。したがってこの定数が
実質的なマスター解像度になる。engine 10 までは書き出し箇所ごとに桁がばらついており
（`.1f` / `.2f` / `.3f` と、svgwrite へ素の float が渡って出る 17 桁）、
**同じキャンバスの上に 1e-4 から 1e-19 までの目盛りが同居していた**。

グリッドの値は上下から挟んで決めてある。

- **下限（再現性）:** プラットフォーム間の `math.sin` の差は相対 2e-16。実測では
  **小数 11 桁目から** macOS と Linux の出力が割れる。グリッドはそこから 4 桁上にあるので、
  どの OS で演奏しても同じ文字列が出る
- **上限（物理）:** 100m の壁へ引き伸ばしても刻みは 100nm。可視光の波長より細かく、
  描く手段の側が先に限界に達する

**末尾のゼロは詰めない。** 桁が固定なら成果物のどの数値も `-?\d+\.\d{6}` に一致し、
**グリッドに載っていることを出力そのものから機械検査できる**。詰めると
`695.45787` が 6 桁グリッドの産物か生の float かを見分けられず、
「丸めてから詰めた」という手順を信じる形になる。

**整数は整数のまま書かれる**（キャンバス寸法・`viewBox` など）。グリッドは小数を持つ値の規定である。

**このグリッドは形の忠実度とは別の軸である。** ストロークは曲線でなく直線の連なりとして
出力されており、実効的な形の解像度はキャンバス比 **2.2e-4**（弦の矢）にある。
桁のほうが 200 倍細かい。**壁面規模の出力で効くのは桁ではなく標本化のほうである。**

### エンジンは後戻りしない（版画としての実装、v2.4.6）

**過去の描画エンジンをシステムとして保持しない。版を選び直す機構も作らない。**

- **Replay は常に最新のエンジンで行う。** `current_render_engine()` は引数を取らず、版を選ばせない
- 記録された `render_engine_version` は**来歴**であって、再描画時の入力ではない
- **当時のエディションの再現は、保存済み SVG の返却で担保する。** 再描画では担保しない
- 再描画時、記録された版と現在の版が違うなら、**UI にその旨を表示するだけ**にとどめる
- DDL 側も同じ。再解釈は常に最新で行い、結果は新しいエディションになる

**これは版画と同じ構えである。**

> 彫りは進む。版木は一方向にしか変わらない。刷り上がった作品は残るが、**彫る前の版木には戻れない**。
> アプリケーション自体を一つの作品として考えるなら、この実装になる。

作品（保存済み SVG とその Score・seed・エディション ID）は**刷り**であり、そのまま残る。
エンジンは**版木**であり、彫り進めた先しか存在しない。
両者を混同して「過去の版木も倉庫に取っておく」ことをしないのが、この設計の選択である。

**その代償として、engine 1〜9 の出力は失われた。** コードも出力も残っていない。
参照コーパス（本書の「参照コーパスによる世代比較」）は engine 10 から始まる。
**だからこそ、現役のうちに刷りを取っておく。** コーパスとは、彫り進める前に取る**校正刷り**である。
版木は戻せないが、刷りは残せる。

**版数だけを記録して出力を残さないのは、彫った日付だけを書いて刷りを捨てるのに等しい。**


### PNG は演奏を写す（v2.7.10、v2.7.11）

**SVG が正本であり、PNG はそれを写した像である。** 像は縮んでよいし、粗くてよい。
**落としてはならない。**

#### 黙って落とすラスタライザを使わない

**PNG 化の経路に、SVG フィルタを実装せずに黙って飛ばす実装を置いてはならない。**
対象は少なくとも `feTurbulence` / `feDisplacementMap` / `feGaussianBlur` である。
これらは**地の粒と材質層の全部**を作っており、飛ばされた PNG は絵として成立してしまう。

**この規則は性能や画質の話ではなく、観測の話である。** 落とす実装を通した PNG は、
**「差が無い」と「差が写っていない」を区別できない**。inku では作品の採否・engine の版上げ・
移植の同一性が、いずれも**二枚の絵を並べて読む**ことで決まる。
写し損ねる道具を挟むと、**その判断すべてが静かに壊れる**。

#### `cairosvg` は使わない

**`cairosvg` は使用を禁じる**（2026-07-27 作者裁定、v2.7.10 で撤去）。
上の 3 フィルタをいずれも実装せず、**例外も警告も出さずに飛ばす**。
2026-07 のセッションで、これが焼いた「きれいに見える PNG」が **4 回、判断の材料にされかけた**。
警告は CLI の stderr・サーバーの起動ログ・docstring・成果物の `png_rasterizer` の四重にあった。
**それでも防げなかったのは、人を誤らせるのがログ行ではなく絵だからである。**
したがって**文書化ではなく撤去する**というのが、この節が定める扱いである。

#### 無い実装より、誤る実装のほうが悪い

**フォールバックを置かない。** 現在の唯一の実装は `resvg`（`resvg-py`）であり、
**それが無い環境では PNG 出力は静かに劣化するのではなく停止する**。
PNG が出ないことは目に見えるが、**質感の落ちた PNG が出ることは目に見えない**。

#### 守り方

`shared/src/inku_analysis/rasterizer.py` を**唯一の入口**とし、server・CLI・
Android 比較ハーネスのいずれもここを通す。番人は 3 つで、

### 配布（v2.4.0）

リリース版はコンテナイメージで配布する。git タグ `vX.Y.Z` の push を起点に GitHub Actions が `ghcr.io/oikawas/inku-api` / `ghcr.io/oikawas/inku-web` を multi-arch（amd64 / arm64）で build & push し、利用者は `deploy/` の compose と `.env.example` で起動する（Quickstart は `deploy/README.md`）。開発は従来どおり bare metal（rsync + systemd）で行い、コンテナは Release タイミングで更新する。標準プラグイン（`server/plugins/`、現在は Nature.leaves）はイメージに同梱される。

**アカウントの前提**: セルフサインアップの経路は設けない。アカウント作成は認証済み管理者による `POST /api/users` のみで、最初の入口は新規 DB 起動時に作られる bootstrap admin（`INKU_BOOTSTRAP_ADMIN_PASSWORD`、8 文字以上）である。この値が無いまま起動したサーバーは誰もログインできない箱になる（値を設定して再起動すれば復旧する。既存アカウントがある DB では何も起きない）。空文字は「未設定」として扱い（v2.4.0）、配布 compose は値の無い起動を必須チェックで拒否する。

`/api/info` の `version` はサーバー実装の版（`server/pyproject.toml`。v2.4.0 で単一情報源化し、リリースごとに採番する）を返す。web の表示版（`APP_VERSION`）とは名前空間が別だが、一体リリースのため通常は数字が一致する。

**デベロッパーモード（v2.4.3）**: 環境変数 `INKU_DEVELOPER_MODE` は、開発者向けの選択肢を画面に出すかどうかだけを決める。無効時は NVIDIA NIM が表示用モデルカタログ（`GET /api/models`、管理者のモデル設定、モデル一覧再取得）から外れ、Build 番号の常時表示（左下レール・ログイン画面・アプリ情報）も消える。**隠すのは表示だけで、実行経路・保存済みモデル設定・履歴のモデル情報・作品ごとの `render_build_number` は無効時も変わらない**（保存済み設定が非公開プロバイダーを指す場合、画面内の選択だけが公開カタログの先頭へ補正される）。配布 compose は既定で無効、開発・ベンチ用 compose は既定で有効。`/api/info` が `developer_mode` を返し、web はログイン前にこれを読む。

### 印の種は、その印を別の印にするものだけから作る

`_seed_for_instruction` は **instruction の dump 全体のハッシュ**だった。
そのため **coerce が書いた色の注記を書き換えるだけで絵が変わり**、`count` を変えると
筆致まで作り直され、構図フラグの A/B が交絡した。

engine 15 では allowlist にする。入るのは **何であるか・道具・幾何・変奏・表面・`arrangement.jitter`** だけ。
**全 49 フィールドの感度は 30 が動き 19 が動かない**（実測）。

> **「count を変えても筆致が保たれる」は `layout="scatter"` のときだけ成立する。**
> `horizontal` / `vertical` / `radial` / `grid` では 12 → 13 で先頭の 12 本も動く。

> **区間を個数で割る配置では位置が動くのが当然**である。

### 地の種は、支持体の名前である

`_texture_seed` も **Score 全体のハッシュ**だったので、**絵のどこを触っても紙の粒が入れ替わった**。
engine 15 では **`material` + `grain` + 演奏 seed** だけから作る。
**濃さを上げると同じ紙が濃くなる**（別の紙が配られるのではない）。

これで **`ground.absorbency` の退役が解けた**。値は一度も描画に読まれていなかったが、
消すと粒配置が動くので退役できずにいたフィールドである。保存済み Score には残っているので、
`contact` / `thickness`（v2.7.2）と同じく**検証前に落として再生する**。

### 雲形は、ほかの閉輪郭と同じ道を通る

`cloudform` は class に `stroke-engine-touch` を名乗りながら、**一度も `stroke_engine` を通っていなかった**。
材質層の 3 機構（輪郭+粒 / `raster-bleed` / `burr`+`plate_tone`）がすべて不在だった。
engine 15 では内部塗りが作る密なポリラインをそのまま手描き経路へ渡す。**雲形専用の合成は書いていない。**

### 角のある図形と `pen` に、材質層を与える

`_render_corner_shape` には材質輪郭の呼び出しが**そもそも無く**、`triangle` と `polygon` は
材質輪郭を持つどの道具でも裸だった。**本番で最も使われる `pen`** も本体のストロークだけだった。

### 強さは距離ではない

材質強度の梯子は、m1 → m2 → s1 と「材質層が読みにくい」への対処を重ねるたびに
**`outline_offset` の倍率を上げ**（最終的に 2.8 倍）、**下限 3.5px** を敷いていた。
**帯の実測半幅と比べると、痕跡は `pencil` で 4.5 倍・`chalk` で 6.5 倍の距離**にあり、
**痕跡ではなく第 2 の輪郭として読めた**。

engine 15 では **倍率を 1.0・下限を 0 にした**。仕様表の値はもともと半幅の 0.7〜2.3 倍で書かれており、
**表は悪くなかった**。濃さの梃子（`outline_opacity` の 1.8 倍と下限 0.50）は**触っていない**。

> **強さは濃さが持つ。距離は強さの梃子ではない。**

## engine 14 — 一枚の方眼と、暴れるの到達（v2.7.0）

- **量子化された格子を、作品ごとに 1 枚に統一した**
- **「暴れる」を輪郭・弧・塗り・ハッチへ届かせた** — engine 12 では線プリミティブにしか届いておらず、
  **説明と実装が食い違っていた**（円や四角は ON でも出力がバイト一致していた）

**動いた 126 / 不変 221。** コーパスは 228 → 347 件へ増えた（暴れるの新規ケース）。

詳細: [CHANGELOG v2.7.0](../history/changelog-v1.72-v2.4.ja.md)

**engine 13 が残した 2 つの穴を、演奏結果が変わる 1 つの版として塞いだ。**
どちらも出力が動くので、まとめて 1 つの版にしてコーパスの再凍結を 1 回で済ませている。

### 方眼は紙の性質であって、置かれた対象の性質ではない

engine 13 の格子は目盛が**ストローク長に比例**していた（`step = 長さ × 0.018`）。その結果、

- **長さの違うものは目盛が違う**（100px → 1.8px、400px → 7.2px、800px → 14.4px）
- **同じ長さでも置かれた位置で位相が変わる**。同一長の線を 30 箇所に置くと **30 種すべて異なる図**になった
- 1 枚の絵の中に**大きさの数だけ別々の方眼**が同居していた

engine 14 では目盛を **`キャンバス短辺 × quantize`** で決める。`quantize` の値は `0.018` のままだが、
**意味が「ストローク長に対する比」から「キャンバス短辺に対する比」へ変わった**。
`stroke_engine` はキャンバスを知らないので、**renderer が px へ直して `grid_step` として渡す**。
長さ相対の経路は残していない（切り替えフラグも既定値も置かない）。

- 正方 1000px で **18.000000px**。短辺基準なので**アスペクトで変わる**（a4 12.726px / oban 12.006px /
  vertical 10.116px / **pillar 3.600px**）。これは帰結であって不具合ではない
- **同じ絵の中のすべてのストロークが同じセルへ落ちる。** 被覆セルの一辺は 1 つの Score で単一の値になり、
  中心は同じ目盛の整数倍に乗る（大小 3 対象を同居させた実測で、格子から外れた座標が 188/194 → **0/194**）
- **方眼が対象の大きさで縮まなくなったので、連続する標本が同じセルへ丸め込まれることが起きる。**
  重なったセルは重ねて描く（一意化しない）。作者はこの見えを含めて 18px を選んでいる

### 暴れるが輪郭へ届く

engine 12 の「暴れる」は **`line` プリミティブにしか届いていなかった**。実測では
**11 道具 × 8 プリミティブ 88 組のうち 63 組が ON/OFF でバイト一致**しており、
`SPEC.ja.md` §13.4 の「作品全体に一つのトグル」という位置づけとずれていた。

engine 14 では `synthesize_along`（円・楕円・三角・四角・多角形・弧・塗り・ハッチ）にも
中心線ジェスチャを足し、`wild` を通す。**OFF の出力は 1 バイトも変わらない**（既存 228 件のうち
OFF で動いたのは格子の変更による 7 件だけである）。

**バイト一致してよいのは 25 組だけで、それぞれ理由が違う。**

| 一致してよい組 | 件数 | 理由 |
|---|---|---|
| 全 11 道具 × `cloudform` | 11 | `cloudform.py` が `stroke_engine` を通らない（**engine 14 でも直していない既知の穴**） |
| `rotring` × 残り 7 プリミティブ | 7 | 道具文法の `gesture` が 0。機械の極 |
| `computer` × 残り 7 プリミティブ | 7 | `periodic` が `WILD_GAIN` を飛ばす（本書の「engine 13」） |

### 素朴な移植では壊れる 3 点

直線のジェスチャをそのまま輪郭へ写すと破綻する。**いずれも試作で実測して仕様に落とした。**

1. **弧長で振幅を決めてはならない。** 閉輪郭の周長は寸法ではない（多角形が星形になった）。
   **閉輪郭は `周長 / τ`＝半径相当で測る**
2. **ジェスチャの平均を差し引く。** 平均が 0 でないと図形全体が伸縮する（円が一回り縮んだ）。
   **大きさは楽譜が決めるものであって、演奏が変えてよいものではない**
3. **角（anchor）の手前で窓を 0 へ落とす。** 意図へ戻される頂点の隣にジェスチャが乗るとトゲが出る

### 材質は墨に追随する

輪郭と弧の材質アウトライン（`class="material-outline"`）は**幾何から引かれていて、
演奏された中心線を見ていなかった**。暴れるを届かせると **9 組すべてで墨だけが動き、材質が幾何の上に
取り残された**。これは engine 12 が直したのと同じ型の不具合である（材質層が中心線に追随せず、
独立した罫線として背景に残る）。

**暴れる ON のときは、輪郭・弧の材質アウトラインと粉を演奏後の中心線から作る。**
OFF のときは engine 13 のままである。

### 版とコーパス

`render_engine_version` は `13` → **`14`**。参照コーパスは **347 件**（`corpus_format_version` は
`"1"` → `"2"`。ケースの入力に `wild` が加わったため）。`changed_from_previous` は **126 件**で、
内訳は**既存 7 件**（`A-computer-*` から `cloudform` を除いたもの）と**新規 E 群 119 件**（暴れる ON の
全数 88 + 塗り 15 + 面 16）、**不変 221 件**である。**手の 10 道具は 1 件も動いていない。**

## engine 13 — コンピュータのてざわり（v2.6.0）

- **道具に「コンピュータ」を足した。** 幅と経路が固定の刻みに落ちる。**誤差なく反復する**のが核
- 反復は seed でばらつかない。材質層は直線で、dash は全数が同じ値

**動いた 8 / 不変 220。動いた 8 件は新しく足したコンピュータのケースそのもの**で、
**既存の 220 件は 1 件も動いていない。** 道具を 1 つ足しても既存の演奏を動かさなかった、という記録である。

詳細: [CHANGELOG v2.6.0](../history/changelog-v1.72-v2.4.ja.md)

**11 番目の道具「コンピュータ」を足した。** 核は「手が震えない」ではなく **「誤差なく反復する」**。
手は同じ値を二度出せない。計算機は同じ値しか出せない。**周期＝線に沿った方向の反復、
格子＝空間方向の反復**で、同じ性質の 2 軸である。

`rotring` との区別はここで立つ。**rotring は反復すべき揺れを持たない**（道具文法が全項 0）。
**コンピュータは揺れを持ち、それを正確に繰り返す。** したがって engine 11 の対称エンベロープへの
後戻りではない。engine 11 のそれは**選べない既定**であり、engine 13 のこれは**選べる語彙**である（本書の「エンジンは後戻りしない」と衝突しない）。

- **反復は seed でばらつかない。** 機械の周期（energy の 5 周期 + 10 周期、gesture の 2 周期）も
  幅の段も格子も定数で、`render_seed` を引数に取らない。**同じ Score なら seed を変えても
  出力はバイト一致する**（手の道具は一致しない）。ただし**配置と運動語彙の seed 依存は上の層の話**なので従来どおり残る
- **「暴れる」は効かない**（`SPEC.ja.md` §13.4）。暴れは手の話であり、`rotring` と同型に扱う
- **格子**: 中心線の座標を格子へ丸め、幅を 4 段に落とす。**engine 13 の刻みは `ストローク長 × 0.018` で、
  対象ごとに別の方眼になっていた。engine 14 で `キャンバス短辺 × 0.018` の 1 枚の方眼へ改めた**（本書の「engine 14」）
- **閉じた輪郭はロットリングとほぼ同じでよい。** 閉輪郭専用の半径変調は作らない。それが CG のテイストである

### 材質は「標本化の残り」である

手の道具の材質層は**道具が線の脇に落とすもの**である（黒鉛の粉、筆の毛、蝋の削れ）。
計算機にはそれがない。**あるのは、格子へ丸めるときに捨てた差である。**

**幾何が「誤差なく反復する」。材質が「誤差を捨てた跡」を見せる。**

標本ごとに、丸める前の位置と丸めた後の位置の差（残差）を取り、**残差が 0 でない標本にだけ**
格子 1 セルの正方形（`class="raster-bleed"`）をストロークの下に敷く。セルは**格子に丸めた座標**に置き、
濃さは**残差の大きさに比例**する（セル半分ずれたときに上限 0.45）。seed を使わないので、
**同じ図なら同じ跡が出る**。

**端点は意図へ固定され、多角形の角は anchor で意図へ戻される**ので、それらの標本は残差を持たず
セルを出さない。直線は 41 標本のうち 39、四角は 80 のうち 76、弧は 62 のうち 60 がセルになる。

**この材質は engine 13 の第 1 版から作り直している。** 最初の版は「まっすぐな定規の線 + 全数同一の
等間隔 dash」だった（旧作 `rh2:9e991c…` の「直線の雨」を道具の性質として置き直す設計）。
実装して目視すると、**材質層が意図した始点→終点に固定される一方、演奏された中心線は最大 55px 離れる**ため、
点線が線から切り離されて独立した罫線に見えた。**絵画上の意味を持たないので捨てた。**

## この文書の作り方

- **一覧の数値は手で書かない。** `server/reference/render-engine-*/manifest.json` の
  `changed_from_previous` と、その版のディレクトリに置かれた SVG の枚数から取る
- **版を上げたら、この文書に 1 節足す。** 節には必ず**不変の側**を書く
- **日英 2 版がある。** `render-engine-history.ja.md` が正本で、英語版はそれに従う。
  `server/scripts/check_docs.py` が見出しの対応を検査する
